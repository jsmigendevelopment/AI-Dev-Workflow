# Changelog

All notable changes to the kit are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The kit's version is the one at the bottom of `AGENTS.md`. The CLI on npm carries the same version.

## [Unreleased]

### Added

- **No Actions, part 3: `npx onrails ci local`, and doctor and preflight warn about workflows (#133).** `npx onrails ci local` turns GitHub Actions off for the repo first (`PUT /repos/<owner>/<repo>/actions/permissions`, `enabled=false`), then opens an issue and a pull request on `fix/<n>-no-actions` that removes `.github/workflows/` and writes `ci = "local"` to `docs/stack.md`, from a temp worktree, so your checkout isn't touched. It asks once below Full and nothing on Full; `--dry-run` lists the files and the API call. `onrails update` runs it for a repo on `ci = "local"` that still has workflow files. `doctor` gives a ✗ for workflow files or Actions on, with the fix `npx onrails ci local`, and preflight prints the same as a warning under its table, reading only files before the repo is read. The agent-file guard already flagged a new workflow; a test now pins it.
- **`/update` and `npx onrails@latest update --all`: one command brings onRails to its latest (#178).** In order: the Claude Code plugin (`claude plugin marketplace update onrails`, then `claude plugin update core@onrails`) and the Codex plugin (`codex plugin marketplace upgrade onrails`), each only when the tool is on `PATH` and its plugin is installed, run by full path with no shell (a Windows `.cmd` shim through `cmd.exe` by its full path, quoted, so a path with a space works), never a copy the project ships: the `PATH` search skips relative entries, entries whose real path is inside the project or the current folder, and every `node_modules/.bin`, and the home folder never counts as the project unless it is one, so a `claude` in `~/.local/bin` runs when you start it from `~` (a project that holds `HOME` stays a project, the project is the nearest folder with `.onrails.json`, so a run from a subfolder skips its tools too, and only `~` as a project gets the commands to run a skipped tool by hand); the global entry skills, when `init --global` was used, refreshed the way it does; the project's kit, as `update` does, inside an onRails project, from any subfolder (else it says it skipped it); then `doctor` and a summary of each part's version before and after, ending with "run `/reload-plugins`" for Claude Code. A part that throws is a FAILED row, and the rest still runs. `--dry-run` prints the plan and runs nothing. Plain `update` is unchanged. The new `update` skill runs it from a temp folder under `/tmp`, outside the project (on Full it asks nothing; below Full it shows the plan and asks once), falls back to the plugin's own CLI found from its install record, never a path in the project, and ships in the kit and, copied as it is, in the plugin. The README's "update the plugin by hand" line, the cheat sheet and `cli/CLI.md` point to it. 24 tests in four files, with fake `claude` and `codex`, a temp home and a `PATH` that never holds Node's own folder (a text scan of the tests and a check of each child's `PATH` guard it). Decision rows 77 and 78.
- **Clean up what you start: a process registry, pause and stop, session-end cleanup and `npx onrails ps` (#126).** Agents start every background process through `node .agents/skills/ask/scripts/procs.mjs start --why "..." --until "..." -- <command>`, which runs it in its own process group and records its PID, start time, owner session and stop condition in `.onrails/procs.json` (the repo's main checkout, shared by worktrees, ignored by git) or `~/.onrails/procs.json`. Starting one without a reason and a stop condition is refused. `AGENTS.md` gains rule 15: stop what a task started when it's done; "pause" keeps only the dev server, marked paused, and a watcher stops it after `[workflow] pause_hours` (2, new in the profile template) or at session end; "stop" ends everything the session owns, timers and scheduled tasks too; both write a resume note and show `procs.mjs list --mine`. `ask` gains "Pause and stop" with both lists of words, and `build`, `afk`, `back` and `coordinate` register and stop the dev server. "brb" alone now means pause, not `/afk`. A new `SessionEnd` hook for Claude Code and Codex stops the session's processes and orphans (their owner session is gone): TERM to the group, then KILL after 5 seconds from a detached reaper, because Codex caps the hook at 3 seconds. The session-start hook warns about orphans. New `npx onrails ps [--stop <id|all|stale|pid>]` lists age, owner, CPU and memory, and asks before it stops a PID the registry didn't record; on Windows it uses `taskkill /T`, then `/F`. `doctor` warns about stale ones; `list`, `ps` and `doctor` only read. The registry is a file, so one check runs before every signal, on every record: a PID above 1 that isn't the script, its parent or the agent, a start time that matches the live process (a record without one is never alive, and `start` never writes one), and for a group signal a process that leads its own group. A PID the registry didn't record, `stop all` and another live session's id need a yes, or `--yes` after one. A registry that git tracks, or a symlinked registry folder, file or logs folder, is never read or written, and the temp file and logs are opened without following a symlink. After the grace, KILL also reaches a group whose leader has exited while a member is left. `qa` starts its local server through the registry. The script is six files, each under 300 lines. 31 tests: on a fake machine with no real signals, through the CLI binary, and one that starts and stops a real child it owns. New opt-in eval `clean-up-server` for AC-6 (a fuller one is #151).

- **Preflight: every sandbox blocker in the first minute (#100).** New `npx onrails preflight`, also in the kit as `node .agents/skills/ask/scripts/preflight.mjs`, so it runs when the registry is the blocked thing. It probes the agent's own session in about 10 seconds: repo write, `.git` write (a temp branch), the package registry the project's `.npmrc` names, GitHub (`gh api rate_limit` and `git ls-remote`), loopback, headless Chromium when the project's tests use Playwright, Node and the package manager against `engines` and `packageManager`, and the model and effort the session can see. It drafts ONE "Setup step for you" with a numbered fix for every row still blocked and a `Tried:` line. `/idea`, `/join`, `/back` and `build` run it first, and `AGENTS.md` gains rule 14, "Preflight before you build", so it holds even when no skill fires (on Haiku 5.5 the eval failed 3 of 3 runs without that line and passed 3 of 3 with it [measured, 2026-11-25; the run's log isn't in the repo]). `ask` gains `references/preflight.md`: fix in one batch, never one message per problem, and never scaffold while installs are blocked. `--record` writes an `Environment:` line to `docs/state.md`, and `--if-changed` skips every probe when that line says ok and the sandbox hasn't changed. ### Changed

No ⏳ decision and no `needs-human`, only an ℹ️ FYI. Below Full, nothing changes. Decision row 90.
- **The `clean-up-server` eval checks what is really left running (#151).** Its fixture's server now listens on `PORT` or a free port and writes its PID and start time to `server.pids` next to the repo. The good, bad and shortcut transcripts start real servers and run from a new `evals/test/clean-up-server.test.mjs`. Folded in instead of a second `nothing-left-running` scenario (`docs/decisions.md` row 76).
- **Keys on Full: the person only signs in and pastes (#168).** On Full, and below Full after one yes, the `secrets` skill's new "Keys on Full" opens each provider's page in the browser the session has (Claude in Chrome, then the built-in browser; never computer use, which can't click in a browser and screenshots the whole screen), asks only for the sign-in, fills in the key's name, scopes, resources and expiry from the provider file, opens where it goes first (a new terminal window already running `pnpm connect <provider>` when its shell is on the person's machine, with the app folder passed as its own argument so a space or a quote in it works on macOS, Linux, PowerShell and Git Bash; the one command otherwise or when no window opens, or the destination page), then hands the person the click that shows the key and any step after it (such as Stripe's two-factor code), the copy and the paste. It checks by name with `pnpm connect --dry-run`, or `wrangler secret list` and `gh secret list` in a pack without the script. It never presses the button that shows a key, never reads, copies or screenshots a value, never signs in for the person, stops on any paid plan or card, and keeps production keys an always-stop item. With no browser it sends one "Setup step for you" with every link and `pnpm connect`, in one sitting, and the loop goes on. Every row that makes a secret ends "Stop there: the person presses **<button>**"; Entra's API permissions come before its client secret. `AGENTS.md`'s outside-the-repo line and `ask`'s "Setup step for you" say to do every step first. New test `cli/test/keys-on-full.test.mjs`.
- **Releases are cut only when the owner asks.** `RELEASING.md` says so: no version bump, tag or publish after merges on any automation level.
- **No GitHub Actions, part 1: the merge gate runs locally (#131, part of #98).** `coordinate` step 6.1 no longer waits for CI. An agent other than the builder (the coordinator, or the code reviewer when its brief says so) makes a clean worktree of the pull request's exact head in a fresh `mktemp -d` folder, runs `check` and then `test:e2e`, tries once to post the `onrails/check` commit status through the REST API, and posts one comment whose first line is `Checks: pass @ <sha>` or `Checks: fail @ <sha>`. That comment is the record `coordinate` merges on, at the exact head. The local gate only runs the loop's own branches: a new `own-branch.mjs <n> --repo <owner>/<repo>` passes only when the pull request's branch is in the repo, not a fork; its author has write access or higher; the branch is `feat/<n>-<name>` or `fix/<n>-<name>` in plain characters; and its issue has a claim from a login with write access, as a whole line in the claim's form (claims now name the branch, and `build` run alone adds one). An access check that gets no answer (a proxy's 403, a 5xx, a rate limit, the network) is an API error, exit 2, never "no write access"; where a proxy refuses the permission path, the token's own login is checked through the repo's `permissions`. The agent-file guard fails on such an error instead of dropping the voter, so a hidden fail can't let a pass win. Any other pull request is never checked out or run, and it never reaches review, `qa`, the security review, the human gate or the merge: it's labelled `needs-human` and goes to the person as one ⏳ decision. Every command carries the head's full sha and the folder's path, never a shell variable, and the worktree's `git rev-parse HEAD` must equal the sha before `check` runs, or the record is `Checks: fail`. Where the tool allows it, the checks run with deploy and API tokens unset. The status is best effort: some proxies refuse that API path, so a refusal goes in the comment and the gate goes on. After each merge, step 8 checks main's new head the same way and writes a new `Main's checks:` line in `docs/state.md`, which `afk` and `back` read. Workflow results (failed, queued, not started, billing errors) never count, on pull requests or on main; a repo that still has workflows gets one ℹ️ FYI suggesting their removal, noted under "Gotchas" so it isn't repeated. The agent-file guard runs from the session before every merge with a new `agent-files.mjs gate <n> --repo <owner>/<repo> --head <sha>`: the live decision at that head, with the level read from the default branch, and no workflow run needed. The weakening review's comment is all it needs: no label to start a run. `verify-run` still works where the workflow runs, and is no longer required (`automation`'s `references/full.md`). In local mode the `Checks:` line goes under `## Comments` in the issue's file in `docs/issues/`, and when GitHub is rate-limited the status and the comment are queued and posted before the merge is replayed. `AGENTS.md` ("Code") and `build` gain the rule: never add, enable or depend on a GitHub Actions workflow, and find the session way to run a tool that asks for one. `pr-review` reads the local checks, not CI. `docs/decisions.md` records the owner's decisions of 2026-11-26. New opt-in eval `ci-never-starts`, whose checks read actions, not wording: a `check` run, in a worktree of the head sha, the `Checks: pass @ <sha>` line in the issue file, the head merged, and an FYI sent.

The TanStack Start pack: `pnpm deploy:preview <n>` (a preview on the test Worker and its pull request comment), `pnpm deploy:test` (main to test, the smoke test, a rollback on any failure after the deploy), `pnpm deploy:production --confirm "deploy production"` (only after the person's yes), `pnpm check:merge` (what CI added on top of `check`: budgets, migrations match the tables, audit, licences, Clerk files, `docs/research`, gitleaks, Semgrep, screenshots; it skips what the machine can't run and says so), `pnpm pr:rules <n>` and `pnpm test:visual --docker`. Test and production deploy only when the checkout is exactly GitHub's main, a preview only from the pull request's exact head with no uncommitted changes, and the deploy output is masked. All three install from the lockfile first. A failed production migration or deploy step prints the restore command and never runs it. `setup-github.mjs` requires only the `onrails/check` status, and only after a probe status posts (otherwise no status, and it says why); it swaps the old workflows' checks for it in the rule it made, or drops them when statuses can't be posted. `test:visual --docker` mounts the git root, so it works from the monorepo's `apps/web`. The research library template's check runs from the session too. Follow-up for the deploy keys: #139.

- **The process registry is stricter about what it signals (#156).** A group signal is refused when the group holds the script, its parent or the agent. A PID above 2147483647 in one record no longer stops the survey of the others. `stop all` and `stop <id>` ask before stopping another session's record that has no agent recorded. A registry is never read when `git ls-files` fails, when another user owns it, or when the group or others can write it, and an index entry must be the registry of a git repo the user owns. The registry file is opened once, without following a link or waiting on a FIFO, and checked and read through that same open file, in every read and in each update. Its folder and logs folder must be the user's and closed to others (only `~/.onrails` may be group-writable). The registry is now written owner-only, its folders `0700`. A registry others can write, as one written before at `0664`, gets the `chmod 600` that fixes it instead of "delete that folder", and `list`, `ps`, `stop` and the session-start hook name it instead of saying nothing is running. A repo's root must be closed to others, and to its group unless the root is sticky or the group is the user's own. The index is read through one checked open file too, and `~/.onrails` may be group-writable but never world-writable. A group-writable root also needs a clear answer that it has no POSIX ACL, from `getfacl` or GNU `ls`, and a group counts as the user's own only if `getent passwd` (when it is there) lists no one else in it. `doctor` names a registry skipped for its mode, with its `chmod` line, and an index written at `0664` before is named too and keeps its entries on the next write. Git's answers last one command, and the watcher checks the registry again before each pass. - **Tests for the Clerk guards that nothing failed without** in the TanStack Start pack. An e2e check that a valid cookie plus a bare or inexact bearer token is a 401 and that Clerk never saw the cookie (`x-clerk-auth-status`), so unwiring `requestForClerk` fails it; a unit test that the `@clerk/backend` dev dependency is the version `@clerk/tanstack-react-start` resolves, so the header parity test can't go stale. On `/api/v1`, Clerk's own query parameters no longer reach Clerk: a junk `__clerk_handshake` made a development instance throw (a 500), and `__clerk_redirect_url` (an open redirect), `__clerk_db_jwt` and `__clerk_synced` started a redirect. `requestForClerk` drops every `__clerk*` parameter there, and any redirect Clerk still answers with on the API is the uniform 401 (#20).
- **A crafted link can no longer send a tester's Clerk dev session to another site (#66)** in the TanStack Start pack. On a development instance, `@clerk/backend` answered `/notes?__clerk_redirect_url=https://evil.example` with a 307 to that site carrying the dev browser token (`__clerk_db_jwt`). The request guards now answer a `__clerk_redirect_url` or `__clerk_satellite_url` that isn't on one of the authorized parties with a 400 on every path (the API already dropped them, so it stays the 401), Clerk no longer sees the client's `X-Forwarded-*` or `Forwarded` headers, which put a spoofed host in its handshake URLs, and any redirect Clerk itself throws outside the parties and its Frontend API, or to the Frontend API with a `redirect_url` off the parties, gets the same 400. The development sign-in, handshake and satellite sync flow is unchanged and tested; production instances never take that path.
- `.clerk/` (Clerk claim files and temporary keys) is git-ignored in both packs, and CI fails if anything under it is committed.
- **The first pull request can merge now.** `setup-cloudflare` deploys the test Worker once, as the Coming soon page, so previews have a Worker to upload to. `--no-first-deploy` skips it. If the test Worker is missing, the `preview` job fails and names the fix (#3).

### Being built

- A needs-you convention: one clear way for agents to flag what's waiting on you.
- A status board: where every issue and pull request stands, in one place.
- A "Coming soon" page that keeps an app private until you choose to make it public.
- Permissions by relationship (ReBAC): a built-in engine behind a swappable port, and `authorize()` returns a proof the repository needs. The notes example uses it, so agents copy the real pattern.
- Go-style results: services return a value or a typed error instead of throwing.
- An app map: every file belongs to a named area, `pnpm map:check` fails on a gap, and the loop never runs two issues on the same one-at-a-time area.
- One-command dev: `pnpm dev` checks what's missing and names the fix, then migrates, seeds and waits for the health check.
- Tests for the kit itself: scripted sessions replayed each release to prove the agents still follow the rules.
- An incident skill: find the cause, roll back, open the fix issue, write what happened.

- **Renaming the kit to OnRails.** The npm package becomes `onrails`, and the plugin's short name is `or`, so commands read `/or:idea`, `/or:join`, `/or:back` and `/or:afk`. The repo, CLI, plugin and README move together in one pull request.

### Planned, after 0.4

- Tree-shakeable framework packages, and code fixes on update.
- AI cost per issue on the board, privacy export and delete, uptime checks and backup-restore drills.

- **A one-time GitHub setup script**, sized to your plan.
- **A personal profile** for what never changes for you, and app presets for the product grill.
- Hooks for Claude Code: a session-start hook that gives every session the branch, the last commit and `docs/state.md`, and a desktop notification when an agent needs you.
