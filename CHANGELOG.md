# Changelog

All notable changes to the kit are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The kit's version is the one at the bottom of `AGENTS.md`. The CLI on npm carries the same version.

## [Unreleased]

### Changed

- **Show it as soon as it renders (#99).** Slice 0 starts with the running app: the dev server, the link and one line on what to see, before CI, secrets or the test deploy. `build` gains step 11 and a "Show it" section: start the dev server in the background, run on the fakes when keys are missing and say what's off, and give the link, the page and the try line. In a cloud session, screenshots (desktop and phone, light and dark) plus the local command instead. `coordinate` passes a builder's look to the person before the merge, and adds the local command to "To try". `/back` offers to start the dev server; `/back` and `/afk` stop it. `stack-tanstack-start` starts `pnpm dev` on port 3000 before `pnpm check`. `pyramid`, `idea` and the pyramid template follow. New eval `show-it-early`; the runner's default cap goes from 18 to 20 runs.

## [0.5.3] - 2026-11-24

### Added

- **README signatures come from the profile (#90).** `npx onrails signature` builds the owner's sign-off from `[me.signature]` (and `[me.signature.personal]`) in the profile: full or compact, HTML or `--markdown`. `--write README.md` keeps one block between `onrails:signature` markers. It refuses emails, `mailto:` links and non-https URLs, and escapes HTML. `name` and `join` run it when the profile has one. The onRails README's signature is now generated.

### Changed

- **The npm page tells the whole story.** `cli/README.md` is now made from the root README (banner, what onRails is, install, the four commands, the flow, guardrails, stacks) plus `cli/CLI.md` (the CLI reference), with every link and image made absolute so it renders on npm. `node scripts/npm-readme.mjs` makes it; CI checks it; `npm publish` runs it. The README gets an npm badge.

## [0.5.2] - 2026-11-24

### Changed

- **Wireframes start earlier, in two stages, screen by screen (#80).** Stage 1, the grey-box layout, starts in the background when the grill's main-flow topic ends, on the everyday model at medium effort; later topics add screens and the MVP cut drops them. Stage 2, the detailed UI and UX (tokens, states, spacing, motion, the light and dark prototype), starts once look and feel is answered, on the strongest tier at high effort, asking first. Each screen is shown as it's done with "What would you change?". Approval is still one row for the full stage-2 set, before the tech grill. `idea`, `grill`, `routing`, `join`, `pyramid`, the consistency check, the templates, the README, the cheat sheet and the `wireframe-gate` fixture follow.

## [0.5.1] - 2026-11-24

### Added

The library says where things go in `research-library.json` (`research-library/1`, schema in `research/references/library.schema.json`): the report, store, provenance, briefs and data paths with `{slug}` placeholders, the index entries, the provenance schema, its check commands and `private: true`. The `research` skill gains step 9 and `references/library.md`: check the repo is private with `gh` and refuse a public one, write the entry where the manifest says, run its checks, open the pull request. No library? The profile gains `[research] library`, `library_path` and `offered`. The first two are personal: `profile copy` and `init` replace them with a comment in `docs/profile.toml`, agents read them from `~/.onrails/profile.toml` only, and `doctor` flags a project copy that has them. `routing` gains the capture row. 16 tests.
- **Accounts: a fixed split by job or project, never by usage (#76).** The profile gets `[accounts]` (one table per account: label, tool, config folder, projects, jobs) and `[sessions] prefer = "cloud"`. `/idea` (while the wireframes draw) and `/join` (with the keys) ask once about other accounts and give one "Setup step for you" per account, with sign-in commands checked against Claude Code 2.1.331 and Codex 0.171.0 (`CLAUDE_CONFIG_DIR=... claude auth login`; `CODEX_HOME=... codex login`, `--device-auth` without a browser). `routing` adds the rule line, a "Where a job runs" table (cloud first) and `references/accounts.md`. `coordinate` and `/afk` write a ready-to-paste prompt for a job that belongs to another account instead of running it, and at a usage limit that account's work waits for the reset with an FYI; it never moves. `/back` reports each account's waiting work. New `npx onrails accounts`, and `doctor` checks each account's config folder exists without looking inside. 8 tests.

### Changed

- **Install the plugin for your whole account.** The README, the cheat sheet and `init --global` now use `claude plugin install core@onrails --scope user` from a terminal, and say to pick "user" when installing from inside Claude Code. A project install only works in one folder, which is why `/or:` was missing in new threads.

## [0.5.0] - 2026-11-24

### Added

- **Thin steps: each pass is cut into the smallest changes the person can try.** A slice ("the shared list") is now cut into steps ("add an item"), and one step is one issue and one pull request. `pyramid` gains the thin test (a person can try it, it cuts through every layer, size 4 or under, one thing), a count rule (fewer than two steps per slice means you listed slices), one schema change per slice per pass, and `references/slicing.md` with seven ways to cut, the hamburger method and what to do when the checker fails. The `pyramid.md` template gets a steps table (step, slice, try it, size, after) and a "Done means" list: the kit's definition of done. `issues` writes one issue per step with a "Try it" section and aims for complexity 4 or under; a 5 to 7 says why it can't be cut. The consistency check gains a thin-steps item.
- **A plan checker.** `pyramid/scripts/check-plan.mjs` (no dependencies) reads the steps table and fails a step named after a layer, a step with no try line or a developer's check for one, a size above 4 with no reason or above 7, more than one big step in three, fewer than two steps per slice, a pass 1 that skips a slice, and steps out of order. It prints steps per slice, the median size, how many can start at once and the longest chain. `pyramid` step 8, `issues` before it writes anything, `/idea` and the consistency check run it. A "Checking a plan" section in `pyramid` says to run it before judging a plan someone else wrote. 19 tests and a case table.
- **The pass gate keeps moving.** The loop no longer stops dead at the end of a pass. The audit and the cleanup pick need no person, so they start at once, and the loop builds what they find, labelled `gate`. New scope still waits: the person tries it, then says go to the re-plan. Under `/afk` the loop does the same and stops when the gate work runs out. Cleanup is capped at one issue for every five in the pass that just ended. Feedback about what's built is taken any time and built in the current pass; a new idea goes to `features.md`.
- **Three in flight.** `coordinate` keeps at most three issues claimed and not yet merged ("In flight at once" in `docs/stack.md`, a new switch in `automation`), and claimed work parked on the person counts. It finishes one before it starts another. Hands-on is 1: one builder the person starts.
- **A line on what to try, per merge.** Every step has a try line: what the person does on the test site and what they see. It is in the issue, the pull request, the "ready to try" FYI and a new "To try" list in `docs/state.md`, which `/back` shows first. When the person merges a lane, the ask carries the preview link and the try line.
- **Flow numbers.** `coordinate/scripts/flow.mjs` (no dependencies, no API calls) reads `gh pr list --state merged --json ...` and prints merges a day, hours from pull request to merge (median and 85th percentile), hours from issue to merge, the median and the longest gap between merges, the median size and the slowest pull requests. The retro in `/back` and the re-plan at the gate read it. 5 tests.
- **After launch: cut small, then the way in last, then a flag.** `pyramid` says how half-built work merges once the app is live.
- **Two more behaviour tests.** `plan-thin-steps`: the plan for pass 1 has a steps table, at least two steps per slice, a try line on every step, no layer steps and no big step without a reason. `coarse-plan-rejected`: a plan cut by layer is sent back, with the layer steps named and a try line asked for. Both share `evals/lib/flatshare.mjs`. The runner's default cap goes from 14 to 18 runs.
- **A research dossier on agile flow:** [`research/agile-flow.md`](research/agile-flow.md), with its sources, claims, two measurement runs and a fact-check.
- **Vendor setup recipes (#17).** `secrets/setup/` has one recipe each for Drizzle, shadcn/ui, Tailwind, Stripe, Supabase, Sentry, Resend and PostHog: what to ask first, the vendor's own agent entry point reviewed against its source repo and npm (dated 2026-11-23, `[U]` where unchecked), and the kit's rules on top: no global installs, exact pins, keys only through `secrets` and `pnpm connect`, events only through `track()`, vendor skills never in the repo's `.agents/skills`, third-party installers (`plugins`, `add-mcp`) named and asked about first. The Sentry handoff code is a credential, typed only at a hidden prompt in the person's own terminal. Each add-on's `ADDON.md` points to its recipe, and a CLI test checks all of it.
- **After the MVP: the hourglass.** Past "MVP complete" the pyramid turns upside down and widens. Each layer adds new features (each in thin) plus a pass on what's already there, the core every layer. A pass is an improvement. One layer is planned at a time, with the same gate between layers.
- **One pass at a time, with a gate between passes (#60).** `pyramid` outlines every pass (milestone, slices, one line on "better") and details only the current one. The MVP is 3 passes, Works, Real and Ready; more needs a `decisions.md` reason and the person's yes, capped at 4. Only the core, the supports it can't work without ("does the core work without it?") and the floor go in; an insisted non-core must is asked about once, then capped at pass 1 or 2; other features get their own 1- to 2-pass pyramid. `issues` writes the current pass only and refuses later ones until their gate. A new `pyramid/references/pass-gate.md`: the person tries it, a fresh read-only audit against the plan and the approved wireframes, cleanup capped at about 20%, and a re-plan on the strongest tier (asked first), then the consistency check. `coordinate` stops at the end of a pass with a ⏳ decision, under `/afk` too, and `/back` offers the gate first. The end of pass 3 is "MVP complete" on the test site, not launch: `AGENTS.md`, the stack pack and `/back` say launch is the person's call. The pyramid and MVP templates gain the outline, the per-pass status and the gate record.
- **A research standard for every app, and for the kit's own `research/` (#32).** `docs/research/README.md` is an index: one row per dossier with the question, the decision it fed, the date, the status (`draft`, `current`, `stale`, `superseded by …`), the re-check date and the author's model and effort. `/idea` and `/join` create it from `templates/research-index.md`; dossiers start from `templates/research.md`. Each dossier has a `<topic>/` folder with `provenance.json` (`research-provenance/1`: the exact model ID, effort, harness, dates and brief for every role, `unknown` when not recorded, never guessed), a desk-research store (hypotheses, coverage matrix, append-only `sources.csv` and `claims.csv` with a label on every claim) and a fact-check disposition file; benchmarks add manifest-first, append-only run folders. A fresh-context fact-check comes before `current`. The `research` skill gets reference files for desk research, provenance (with the `Research-Model:` and `Research-Effort:` trailers) and measurements, plus a JSON schema. `scripts/check-research.mjs` (no dependencies) checks all of it, and the append-only rule with `--base`; it runs in the kit's CI on `research/`, ships in the research skill, runs in the app CI templates, and `/back` and `doctor` list stale dossiers. The kit's six dossiers are backfilled: only the competitor scan recorded its model (`claude-opus-5-5`); every other model, and every effort, is `unknown`.

- **Behaviour tests for the skills (#54).** `evals/` runs seven scenarios (the grill, git safety, secrets, test-first inside the fence, a weakened test in review, the wireframe gate, asking before the strongest tier) in Claude Code twice, with the kit installed through the CLI and without. Checks read the transcript and the files; none asks a model. A scenario fails when a check fails with the kit or the kit made no difference. The harness's tests use a fake `claude` and run in normal CI.

It asks *"What would you change?"*, revises until the person says yes, and records `Wireframes approved: <date>, <hash>` in `decisions.md`. `/idea` starts it in the background on the strongest tier once the product grill is confirmed, names the app meanwhile, and runs no tech grill or pyramid before the approval (steps 4–6; later steps move up by two). `pyramid` builds the schema and API from the approved screens and doesn't redraw them; a changed screen goes back through approval, as do new screens in `/join` and big features. The consistency check flags an MVP screen without an approved wireframe. The grill log's coverage map gains look and feel and both wireframe lines, and `/back` resumes a kickoff paused after naming.

- **Review fixes for the thin-steps and rolling-gate change.** The gate is idempotent: steps 1 to 3 of "End of a pass" each leave a mark in the Gate record (the `gate` status, `ask sent`, `audit started`), so the ask goes once and the audit runs once per gate. Fuzzy names ("Booking store") and try lines ("check Sentry"), and an "and" in a name, are warnings. Slice 0 no longer counts toward the big share. A case table in `cli/test/check-plan-cases.mjs` holds must-error, must-warn and must-pass cases.

### Fixed

- **The monorepo-expo pack says `eas env:set`, not the deprecated `eas env:create`,** in its README and `.env.example`, matching eas-cli 27.11.0, where `env:set` creates or updates a variable. The Expo provider file's trap note now says why (#15).
- **Keys from `clerk env pull` work with no rename (#13).** The TanStack Start pack reads the publishable key as `VITE_CLERK_PUBLISHABLE_KEY`, the name Clerk's TanStack Start quickstart uses and its CLI writes; the env schema, `.env.example`, `wrangler.jsonc`, the Clerk connect block and walkthrough, the stack skills and the monorepo pack say so, and the rename steps are gone. The old `CLERK_PUBLISHABLE_KEY` still works, with one `env_name_deprecated` warning in the Worker log; the new name wins when both are set.
- **Clerk tokens are checked against the app's own origins** (`authorizedParties`) in the TanStack Start pack, for the session cookie and `/api/v1` bearer tokens. The list comes from `SITE_URL`, localhost and the test Worker's previews, so there is no new setup step; `CLERK_AUTHORIZED_PARTIES` adds more. A token for another site, or with no `azp`, gets the same 401 as no token, and production with Clerk keys but no origin refuses to start. Native apps, whose tokens have no `azp`, opt in with `CLERK_ALLOW_NATIVE_TOKENS` (bearer on `/api/v1` only); the monorepo-expo pack turns it on. The refusal reason no longer reaches the page or the response headers. The `Authorization` header is parsed exactly as Clerk does (`bearer x` no longer counts), and on `/api/v1` the cookie never reaches Clerk (#12).
- **A look-alike path no longer slips past the path guards** in the TanStack Start pack. The router matched case-insensitively and decoded escaped letters, so `/API/v1/notes` or `/%61pi/v1/notes` reached the API without the body cap, the rate limit or the cookie removal, and `/NOTES` skipped the Worker's Access check. The router is now case-sensitive, and the request guards answer with a plain 404, server functions included, any path Start would resolve to another one: an empty segment (`/api//v1`), an escaped control character or trailing space (`/notes%20`), or anything Start's own `getNormalizedURL` decodes (`/%61pi`, `/%5FserverFn`). Every guard then compares the path Start routes (`canonicalPath`, #18).
- **Three notes from the path-guard security review (#65)** in the TanStack Start pack. A lowercase escape of a non-ASCII character (`/notes/caf%c3%a9`, sent by some API clients) routes like the uppercase one instead of a 404, and every guard compares the path Start routes; escaped unreserved and control characters and a trailing `%20` are still refused. `//x` (Start's 308) and an empty server function ID (`/_serverFn/`, Start's bare 500) are answered before Start's handler by `beforeStart` in a new Worker entry, `src/server.ts` (`main` in `wrangler.jsonc`), with the guards' plain 404 and the security headers; the `sentry` and `jobs` add-ons' entries keep that call. An unknown server function ID gets the `internal` envelope with the security headers, not Start's `Server function info not found` 500.
- **A native token also needs the app's own claim** in the TanStack Start pack. With `CLERK_ALLOW_NATIVE_TOKENS=true`, a bearer token with no `azp` got through from any app on the same Clerk instance. It now needs an `app` claim equal to the new `CLERK_NATIVE_APP_CLAIM`, which the person adds to the instance's session token claims (a "Setup step for you" in the `secrets` skill's Clerk file); no claim, a wrong or non-string one, or the flag without the variable is the uniform 401. Clerk's custom claims are per instance, so this can't tell two apps on one instance apart: one Clerk application per product stays the rule. The monorepo-expo pack sets the variable (#19).
- **Tests for the Clerk guards that nothing failed without** in the TanStack Start pack. An e2e check that a valid cookie plus a bare or inexact bearer token is a 401 and that Clerk never saw the cookie (`x-clerk-auth-status`), so unwiring `requestForClerk` fails it; a unit test that the `@clerk/backend` dev dependency is the version `@clerk/tanstack-react-start` resolves, so the header parity test can't go stale. On `/api/v1`, Clerk's own query parameters no longer reach Clerk: a junk `__clerk_handshake` made a development instance throw (a 500), and `__clerk_redirect_url` (an open redirect), `__clerk_db_jwt` and `__clerk_synced` started a redirect. `requestForClerk` drops every `__clerk*` parameter there, and any redirect Clerk still answers with on the API is the uniform 401 (#20).
- **A crafted link can no longer send a tester's Clerk dev session to another site (#66)** in the TanStack Start pack. On a development instance, `@clerk/backend` answered `/notes?__clerk_redirect_url=https://evil.example` with a 307 to that site carrying the dev browser token (`__clerk_db_jwt`). The request guards now answer a `__clerk_redirect_url` or `__clerk_satellite_url` that isn't on one of the authorized parties with a 400 on every path (the API already dropped them, so it stays the 401), Clerk no longer sees the client's `X-Forwarded-*` or `Forwarded` headers, which put a spoofed host in its handshake URLs, and any redirect Clerk itself throws outside the parties and its Frontend API, or to the Frontend API with a `redirect_url` off the parties, gets the same 400. The development sign-in, handshake and satellite sync flow is unchanged and tested; production instances never take that path.
- `.clerk/` (Clerk claim files and temporary keys) is git-ignored in both packs, and CI fails if anything under it is committed.
- **The first pull request can merge now.** `setup-cloudflare` deploys the test Worker once, as the Coming soon page, so previews have a Worker to upload to. `--no-first-deploy` skips it. If the test Worker is missing, the `preview` job fails and names the fix (#3).

### Being built

- A needs-you convention: one clear way for agents to flag what's waiting on you.
- A status board: where every issue and pull request stands, in one place.
- A "Coming soon" page that keeps an app private until you choose to make it public.
- Permissions by relationship (ReBAC): a built-in engine behind a swappable port, and `authorize()` returns a proof the repository needs. The notes example uses it, so agents copy the real pattern.
- Go-style results: services return a value or a typed error instead of throwing.
- An app map: every file belongs to a named area, `pnpm map:check` fails on a gap, and the loop never runs two issues on the same one-at-a-time area.
- One-command dev: `pnpm dev` checks what's missing and names the fix, then migrates, seeds and waits for the health check.
- Tests for the kit itself: scripted sessions replayed each release to prove the agents still follow the rules.
- An incident skill: find the cause, roll back, open the fix issue, write what happened.

- **Renaming the kit to OnRails.** The npm package becomes `onrails`, and the plugin's short name is `or`, so commands read `/or:idea`, `/or:join`, `/or:back` and `/or:afk`. The repo, CLI, plugin and README move together in one pull request.

### Planned, after 0.4

- Tree-shakeable framework packages, and code fixes on update.
- AI cost per issue on the board, privacy export and delete, uptime checks and backup-restore drills.

- **An opt-in work log.** Your first prompt starts the clock and `/afk` stops it. It lives in your home folder or a Google Drive folder, never in the repo.
- **CLI:** `doctor --fix` offers a fix for each problem and runs it only after a yes. `profile init`, `show` and `copy` manage your personal defaults. `init` installs the Claude Code hooks.
- Public project files: this changelog, a security policy, a contributing guide, a code of conduct, and issue and pull request templates for the kit itself.

- The TanStack Start pack is hardened: security headers and a strict CSP on every response, rate and body limits, accessibility checks on every route, page-weight budgets in CI, and SEO files from the start.
- Making an app public is on the always-stop list, next to deploying to production.
- The README is rewritten, with a path chart and a flow chart.
- The coordinator names every skill from the issue in the builder's brief.

### Fixed
