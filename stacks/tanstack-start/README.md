# TanStack Start starter

A small, working app to start from: TanStack Start (React, TypeScript strict) on Cloudflare Workers, with D1 through Drizzle, Clerk for sign-in, shadcn/ui and Tailwind CSS, TanStack Query, Zod, Vitest and Playwright.

It runs, tests and builds with no accounts and no keys. Without Clerk keys, sign-in is off and every notes call is refused.

It starts secure, fast, accessible and search-ready: security headers and a nonce CSP on every response, rate and body limits on server functions, budgets and Lighthouse checks, axe on every route in both themes, and the SEO files built for you. See [On by default](#on-by-default).

The rules: a module never imports another module, shared code never imports a module, and a service never imports the database, HTTP or an SDK. `pnpm lint` fails if any of that happens (`eslint.config.js`). The owner's code style is enforced the same way: see [Code rules](#code-rules).

**Always use a generator** to create a module, route, section, component or table. Each one writes the right shape, wires it in, and passes `pnpm check` as it is:

| Command                                                   | Makes                                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm new:module <name> [--item <singular>] [--no-route]` | `src/modules/<name>/`: `ui/views`, `ui/sections` (Suspense > error boundary > content, a skeleton of the same shape, ErrorState), `ui/components`, `hooks`, `server` (functions, controller, service, repository port, Drizzle adapter, memory fake, table), `schemas.ts`, `types.ts`, `copy.ts`, tests for each layer; its factory in `composition.ts`, its migration, and the page at `/<name>` |
| `pnpm new:route <path> <module>`                          | `src/routes/<path>.tsx` and, if missing, the module's `<last-part>-view.tsx`; the route tree; the path in `e2e/helpers.ts` (axe and screenshots)                                                                                                                                                                                                                                                  |
| `pnpm new:section <module> <name>`                        | `ui/sections/<name>-section.tsx` from the module's list query, and its test                                                                                                                                                                                                                                                                                                                       |
| `pnpm new:component <module> <name>`                      | `ui/components/<name>.tsx` (presentational) and its test                                                                                                                                                                                                                                                                                                                                          |
| `pnpm new:table <module> <name>`                          | `server/<name>.table.ts` with `id`, `created_at`, `updated_at` (snake_case, epoch-ms UTC), and its migration                                                                                                                                                                                                                                                                                      |

Names are kebab-case; a module name is plural (`todo-items`). A new page needs its screenshots: `pnpm test:visual --update`.

## Set up Clerk

1. Create an application at clerk.com (the free tier is enough).
2. Copy `.env.example` to `.env` and fill in `VITE_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` (or let `clerk env pull` write them: those are the names Clerk's CLI uses). Never commit `.env`. The old name `CLERK_PUBLISHABLE_KEY` still works, with a warning.
3. `pnpm dev`, open `/notes`, sign in.

The server reads the keys per request in `src/server/auth.ts`. The signed-in user comes from the verified Clerk session, never from the request body. The CSP opens Clerk's Frontend API host (read from the publishable key) only when the keys are set.

A session token is accepted only from the app's own origins (Clerk's `authorizedParties`, `src/lib/authorized-parties.ts`): `SITE_URL`, localhost in a local build, and the test Worker's workers.dev URL and `pr-<n>` previews in a test build. Add any other origin to `CLERK_AUTHORIZED_PARTIES` (exact origins, comma-separated). Production with Clerk keys needs `SITE_URL` or `CLERK_AUTHORIZED_PARTIES`, or the Worker refuses to start.

## Turnstile (optional)

Add it only when counters show the cheaper layers are not enough. Create a widget in the Cloudflare dashboard, set `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`, and the note form starts sending a token; `withHumanCheck` verifies it. The script loads on the form's first focus, never on page load.

## Set up Cloudflare

An agent runs this for the person, dry run first:

```sh
node scripts/setup-cloudflare.mjs --dry-run   # reads only: what exists, what it would create or change
node scripts/setup-cloudflare.mjs             # after the person says yes
```

It checks `wrangler whoami` (if not signed in, the person runs `pnpm exec wrangler login`), creates the test and production D1 databases if missing and writes their ids into `wrangler.jsonc`, creates any R2 bucket or queue an add-on declared, prints `CLOUDFLARE_ACCOUNT_ID` and sets it in the GitHub environments `test`, `production` and `preview`, explains how to create the deploy token (its exact permissions), deploys the test Worker once if it doesn't exist yet (deploy-test's commands, as the Coming soon page, so pull request previews have something to upload to; `--no-first-deploy` skips it; never production), and runs the kit's `push-secrets.mjs --wrangler` for the app's secrets. With a custom domain (a production `routes` entry, or `--zone example.com`) and a separate zone token in `.env.cloudflare.local`, it applies the free zone settings: Always Use HTTPS, minimum TLS 1.2, AI training crawlers disallowed (never blocked: that would also stop Google and Bing), and a WAF rule that blocks scanner paths. Bot Fight Mode is recommended once the custom domain exists and is the person's choice (`--bot-fight-mode`): the CSP allows its same-origin `/cdn-cgi/` script on the production domain, and the production smoke test runs on workers.dev, outside the zone. Cloudflare's managed robots.txt stays off (`--managed-robots`): it duplicates the app's own. Run it again any time; it skips what exists.

It also asks how to protect the test and preview URLs, and records the answer as `SITE_PROTECTION` in `env.test.vars`:

```sh
node scripts/setup-cloudflare.mjs --protect access --logins google --allow-emails you@example.com  # recommended
node scripts/setup-cloudflare.mjs --protect access --allow-domain company.com                      # PIN only, a whole domain
node scripts/setup-cloudflare.mjs --protect access --logins github --allow-github-org acme
node scripts/setup-cloudflare.mjs --protect password                                               # a password page in the app
node scripts/setup-cloudflare.mjs --protect none
```

Access puts a Cloudflare sign-in in front of the whole test Worker and its previews, static files included, and creates a service token for CI (`CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET` in the GitHub environments `test` and `preview`). It needs Zero Trust on the account and an account token in `CLOUDFLARE_ACCESS_TOKEN` (`.env.cloudflare.local`).

- **Logins** (`--logins`, comma-separated): `google` (recommended), `github`, `facebook`, `linkedin`, `yandex`, `entra` (Microsoft work accounts), `oidc` (any other OpenID Connect provider). A one-time PIN by email is always on as the fallback. Discord is not offered: Access has no Discord login, and Discord does not document an email in its ID token.
- **Each login needs an OAuth client the person makes.** The first run prints their "Setup step for you" with the exact callback URL, then stops. The client id and secret go in `.env.cloudflare.local` (`ACCESS_GOOGLE_CLIENT_ID`, `ACCESS_GOOGLE_CLIENT_SECRET`, and so on), never on the command line, never printed.
- **Who may sign in:** `--allow-emails a@x.com,b@y.com`, `--allow-domain company.com`, `--allow-github-org <org>` (with the GitHub login). Any match lets them in. Emails are never written to a file.

**Production too, after the person's yes.** `--protect-production all` puts Access in front of all of production (the internal-tool default); `--protect-production /admin/*,/ops/*` only those paths, on workers.dev and the custom domain. Same logins and people. Production is on the always-stop list: dry run first, show the person, and the real run needs `--production-ok`. Its service token goes in the GitHub environment `production`, and the production smoke test sends it.

**The Worker checks Access's token too.** Wherever `SITE_PROTECTION` is "access", every request on a protected path (`ACCESS_PATHS`, default all, minus `OPEN_PATHS`) must carry a valid `Cf-Access-Jwt-Assertion`: signed by the team's key, for this app's AUD, not expired. Anything else gets the 401 envelope. setup-cloudflare writes `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD` and, for production paths, `ACCESS_PATHS` into that environment's vars. `src/lib/access-jwt.ts`, with `jose`.

The password option makes a random `SITE_PASSWORD`, sets it on the test Worker and in GitHub, and shows it once; CI sends it as `x-site-password`. Paths that must stay open (a signed webhook) go in `src/lib/open-paths.ts`.

The app's secrets per environment: `pnpm connect` in your own terminal walks each provider, asks for each value with hidden input and stores it in `.env.local`, `wrangler secret put` and `gh secret set` (stdin only, a yes per destination, production asked separately). `pnpm connect clerk` does one provider; `pnpm connect --dry-run` shows what's set, by name. Or by hand: `pnpm exec wrangler secret put CLERK_SECRET_KEY --env test`.

## Deploys

- **Test:** each push to main applies the migrations to the test D1, deploys, and runs `pnpm test:deployed` against the deployed URL. If that fails, `wrangler rollback` puts the previous version back and an issue is opened.
- **Previews:** each pull request uploads a version of the test Worker with the alias `pr-<number>` and keeps one comment with its URL up to date. It uses the test database and never migrates it. Skipped for forks, Dependabot and the `lane:tiny` label.
- **Production:** Actions → deploy-production → Run workflow, typing `deploy production` in the confirm box. The `production` environment waits for the person's approval where the plan allows a required reviewer. It takes a D1 Time Travel bookmark, migrates, deploys and smoke-tests; on failure it rolls back the code and prints the restore command with the bookmark. Restoring data is the person's call.

**GitHub Free, private repo.** GitHub gives it no environments, environment secrets or required reviewers. `setup-github.mjs` then sets the repository variable `SECRETS_MODE` to `repository`, and the same workflows read repository secrets and variables named `TEST_<name>` (test and previews) and `PRODUCTION_<name>` instead; `pnpm connect` and `push-secrets.mjs` write those names. What is lost: no required reviewer on production, no main-only rule, and every workflow on every branch can read the `PRODUCTION_` secrets, so give write access only to people you trust with production. The production deploy's gate is the manual Run workflow plus the typed `deploy production`. Pro or Team brings environments back (delete `SECRETS_MODE` and set the environment secrets); a required reviewer on a private repo needs Enterprise.

**Going live.** Production deploys with `LAUNCHED` "false" in `env.production.vars`, so every visitor sees "Coming soon" and the smoke test checks that page. Only the person decides to go live: then a pull request sets it to "true", and the next production deploy opens the app (the smoke test then checks the app).

A rollback restores code, never data, so a migration must work with the code before it: add columns and tables first, remove them in a later release. Set `SITE_URL` (a variable on the `production` environment) before the first production deploy, and `APP_URL` only when there is no workers.dev URL to smoke-test. For your own domain, uncomment `routes` under `env.production` in `wrangler.jsonc`, and keep `workers_dev` on: the production smoke test runs there.

## HTTP API (`/api/v1`)

For clients that aren't this web app (mobile, desktop, scripts). The web app itself keeps using server functions.

| Method and path            | Body                                     | Success                                                                    |
| -------------------------- | ---------------------------------------- | -------------------------------------------------------------------------- |
| `GET /api/v1/notes`        | `?cursor=&limit=` (1 to 100, default 20) | `200 { ok: true, data: { items: NoteDto[], nextCursor: string \| null } }` |
| `POST /api/v1/notes`       | `{ title }`                              | `201 { ok: true, data: NoteDto }`                                          |
| `PATCH /api/v1/notes/:id`  | `{ title }`                              | `200 { ok: true, data: NoteDto }`                                          |
| `DELETE /api/v1/notes/:id` |                                          | `200 { ok: true, data: { id } }`                                           |

`NoteDto` is `{ id, title, createdAt, updatedAt }` (times in epoch milliseconds). Every request needs `Authorization: Bearer <Clerk session token>` (from `getToken()` on the client, fresh per request); the session cookie is never accepted here. A failure is `{ ok: false, error: { code, message, fields? } }` with the code's status: 400 `validation`, 401 `unauthenticated` (with `WWW-Authenticate: Bearer`), 404 `not_found` (also for another user's note), 405, 411, 413 `too_large`, 429 `rate_limited` (`Retry-After`), 500 `internal`. Bodies are JSON, at most 64 KiB, with no unknown fields. The schemas are `src/modules/notes/schemas.ts`. Optional `CLERK_JWT_KEY` (the instance's PEM public key) verifies tokens without a call to Clerk.

## CI

`.github/workflows/ci.yml` runs on every pull request and on main, cancelling a stale run of the same branch: `checks` (the commands above, knip, jscpd, the migration lint, a check that migrations match the tables, the bundle budgets and the Playwright suite), `visual` (the screenshot tests, in Playwright's Linux image), `semgrep` (community TypeScript and React rules, free, no account), `supply-chain` (`pnpm audit --audit-level=high` and the licence allow-list), and `secrets` (gitleaks). `agent-files.yml` is the agent-file guard, in its own workflow on `pull_request_target`, so a pull request can't change it: changes to agent rules or check code need a `human-approved` label, or on Full automation a weakening review's pass comment at the head commit. It checks out only the base and runs no pull request code. `pr-rules.yml` fails a pull request without `Closes #<n>` (or Fixes, Resolves) and a `feat|fix|chore/<n>-name` branch, unless it has the `no-issue` label (Dependabot is exempt), and one over 400 changed lines (lockfiles and generated files not counted) without the `large-pr` label. `dependabot-auto-merge.yml` turns on auto-merge for Dependabot's patch and minor development-dependency updates, so they merge once CI is green; it needs "Allow auto-merge" in the repo settings (General) and a branch rule that requires the CI checks. `visual-baselines.yml` (run by hand) remakes the screenshot baselines in CI's image and uploads them.

**Screenshots.** Baselines live in `e2e/visual.spec.ts-snapshots/`, one per page, theme and device. After an intended UI change: `pnpm test:visual --update` (on Linux, or the visual-baselines workflow), look at every changed PNG, commit them. Fonts render differently on macOS and Windows, so baselines made there fail in CI. The deploy workflows are described under [Deploys](#deploys); they use the secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` by name and never overlap (one concurrency group each). Dependabot opens grouped weekly updates for npm and GitHub Actions. `pnpm install` also installs a pre-commit hook (lefthook) that formats and lints the staged files.

Playwright is the browser test runner. A person's own browser (for example Claude in Chrome) is for a look after Playwright passes, never instead of it.
