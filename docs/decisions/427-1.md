# Decision 427-1

- **Date:** 2026-11-28
- **Decision:** A pull request's counted size is recorded on the `job=size-check` record, in a new optional `lines` field, and the size script writes that record itself (#427, part of #374). (1) `pr-size.mjs` takes `--record [issue=<n>] [model=<m>] [effort=<e>] [tool=<t>] [model_from=<why>]`, last on the line. After the count it runs `insights.mjs write job job=size-check pr=<n|null> sha=<counted head> lines=<count> outcome=pass|fail [send_back=size]` next to itself, in the checkout it runs in, so the number, the pull request and the sha are the count's own and no agent types them. Any other key is refused with exit 2 before anything is counted. A count that can't be recorded is exit 2 (`Couldn't record the size`), never a quiet pass or fail. Without `--record` the script behaves as before. (2) `lines` is a whole number from 0 up, held to the format's usual limits, and only on a `job=size-check` record with outcome `pass` or `fail`, with the head `sha` present. A `fail` with lines needs `send_back=size` and a count at or over `SIZE_LIMIT` (1,000, the same number as `pr-size.mjs`'s `MAX_CHANGED_LINES`; a test holds the two equal). Older size-check records have no `lines` and stay valid; every record on main still validates. (3) A fail head now has one record, the script's, with `send_back=size` and the count. `coordinate` step 6.1.1 keeps the old hand-run fail command only as the fallback for a count that still can't be recorded after a retry (that record has no `lines`, so the pull request stays `unknown`). Local mode keeps its own explicit command (`pr=null`), because it has no pull request for the report to bucket. (4) `insights-week.mjs` reads a pull request's size as `lines` on its last size-check record in the week. The three buckets, a new `unknown` row and `All sizes` show pull requests, sent back and the rate. With no size on any record the buckets stay `unknown` as before. (5) A size-check job is the coordinator's own count, not a review run, so `has-records` and `carry` no longer count it as the head's `job` record (a pass now exists at every head that goes on to review, so without this a merge could pass with no review job).
- **Options considered:** (a) A `--record` flag that makes the script write the record, as above. (b) The script prints `lines=<n>` and the coordinator pastes it into the existing `insights.mjs write` command: the smallest change, but the count passes through an agent, which the issue's AC-1 rules out ("written by the script, not by memory"). (c) A separate `size` record kind with its own writer: a clean report, but the issue names `job=size-check` and the send-back record already exists, so there would be two records per failed head. For where the count goes: a new kind `size`; `lines` on `job=size-check` (chosen, as the issue suggests).
- **Why:** (a) is the only option where the count never leaves the script, and it reuses the one writer, so the record is as strict as any other and lands as any other (step 10). One record per head keeps the send-back tables from counting a size send-back twice. Tying the failed record to `send_back=size` and the limit makes the field as tight as `send_back` and the other run-cost fields.
- **Originator:** AI pick, not reviewed (Full automation: the owner, 2026-11-26). The ask is the issue's own words: "AC-1 WHEN the size check runs on a pull request head THEN a record holds its counted lines, written by the script, not by memory."
