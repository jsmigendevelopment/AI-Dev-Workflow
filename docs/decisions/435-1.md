# Decision 435-1

- **Date:** 2026-11-28
- **Decision:** How the add-ons' lint-step test is guarded (#435). (1) The catastrophic `PATHS` pattern was already replaced in #425 (decision 425-1) by one that splits paths on exactly one space, so item 1 needed no code change. What was missing is a guard on the three shapes the issue names: a new test, `cli/test/addon-lint-guards.test.mjs`, edits each of the seven add-ons' ESLint lines in memory to end in a backslash, a `# comment` or a `src/*.ts` glob, runs the shared check in a child process with a 5 s limit, and asserts it fails in under a second with a message that starts `<add-on>: lint step line 2 is not allowed`. With the old pattern put back by hand, this test fails (the child times out). (2) `addon-lint-step.mjs` takes an optional `edit` function that changes the Apply text in memory, so a test can break an add-on without touching its `ADDON.md`. (3) New `assertNoOtherLint()`, called first by `assertScoped()`, so all seven add-ons are covered: it removes the lint step's own sh block from the Apply text and fails if anything left runs ESLint or Prettier through `pnpm`, `npm`, `yarn` or `npx`, runs `pnpm format`, `pnpm fix`, `pnpm lint:fix` or `pnpm lint ... --fix`, or starts a line with `eslint` or `prettier`. The message names the command: `<add-on>: Apply runs \`pnpm format\` outside the lint step`. It flags any ESLint or Prettier run, not only `--fix` and `--write`, because the lint step is the one place an add-on runs them. A second copy of the lint step's own block is flagged too. The prose "Never `eslint --fix .` here" and the file name `eslint.config.js` are not commands and are not flagged; the earlier whole-project check stays. (4) A hand-made new file is now seen when its path has a `/` (`scripts/x.ts` as well as `src/x.ts`), so the lint step must lint and format it. A new file in the pack's root has no `/`, and a bare name like `composition.ts` can't be told from a prose mention, so it is still not seen from prose; the comment says so and says to ship such a file in the add-on's `files/` folder, which is always seen. (5) Test ids: AC-435-1 and AC-435-2 are the issue's; AC-435-3 is item 3, which the issue gave no acceptance check.
- **Options considered:** For item 2: flag only `--fix` and `--write` (misses `pnpm exec prettier .` and a second ESLint run that only reports, which still runs before the types exist); flag only code blocks (misses "`pnpm format && pnpm check`" written in prose). For item 3: any backticked name with a lint-covered extension (flags `worker-configuration.d.ts` and bare file names in prose, which are not files the add-on makes); only say so in the comment (the issue's other option, but the `/` rule costs one line and catches the issue's own example, `scripts/x.ts`). For the hang guard: time the match in the same process (a pattern that backtracks would stall the whole suite, so only a child with a time limit can fail it).
- **Why:** The fix for the hang was already on main, so the work that is left is the proof that it stays fixed. One scan inside `assertScoped` means a new add-on or a changed step is checked by the tests it already runs.
- **Originator:** AI pick, not reviewed (Full automation: the owner, 2026-11-26). The ask is the issue's own words: "Scan the rest of Apply for ESLint, Prettier, `pnpm format` or `pnpm lint --fix`" and "widen the rule or say so in the test's comment".
