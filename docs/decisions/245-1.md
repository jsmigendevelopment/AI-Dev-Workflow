# Decision 245-1

- **Date:** 2026-11-27
- **Decision:** How #245 fences the local gate's run of a pull request's own commands. Step 6.1.3 starts each one through main's `coordinate/scripts/fence.mjs`, run in the head's clone, which wraps it in the operating system's sandbox: bubblewrap on Linux, `sandbox-exec` on macOS. Inside, the command can write only to the clone and its empty home folder, and can't read the coordinator's checkout of main, the login stores in its home folder or the macOS Keychain. Before each command, `fence.mjs` tests the fence from outside and prints `Fence: <name>` for the `Checks:` comment; a fence that's missing, won't start or lets a check through counts as none. With no working fence it runs nothing (exit 3) unless `--unfenced` is given: on Full the gate reruns with `--unfenced` and sends one FYI per run of the loop; below Full it's a decision for the person (install bubblewrap, or run unfenced on that machine), and a person-originated decision that says to run unfenced lifts it. The `env -i` line's proxy clause also names `https_proxy` and `no_proxy`, and drops a proxy address with user info.
- **Options considered:** The agent tool's own sandbox (differs per tool, and the gate can't check from inside that one was used); a container (Docker isn't on every machine, and a daemon is a paid or heavy install on some); a separate OS user (needs admin rights and changes the person's machine, out of the issue's fence); the operating system's sandbox programs, wrapped and checked by one script.
- **Why:** bubblewrap and `sandbox-exec` are free, need no change to the machine beyond a package install, and are what agent sandboxes use on each system. One script means one place to check the fence before every command, so "a sandbox was used" is tested, not assumed. Full never waits (the owner's words, 2026-11-26), so it runs with an FYI; below Full, running the head's code as the coordinator's own user is the person's call.
