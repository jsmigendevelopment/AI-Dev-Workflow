# Decision 740-1

- **Date:** 2026-11-28
- **Decision:** `config get` (#708, #733) gets a generic second layer, and no allowlist. (1) **Value:** one token with no space, 20 or more characters, holding a letter and a digit, is refused under any name; a value with `://` goes by the URL rule instead. (2) **URL password:** `://user:rest@` where `rest` holds a raw `/` is refused. A port before a path with an `@` (`https://host:8443/a@b`, pinned by AC-733-3) stays readable: it is told apart by a non-empty host and 1 to 5 digits then `/`. That port exception holds only for the schemes `http`, `https`, `ws`, `wss` and `ftp`; for any other scheme (`mysql`, `postgres`, `redis`, `mongodb`, `amqp`) digits then `/` ahead of an `@` are a password and are refused (round 1 of the review, #744). (3) **Value starts and shapes:** `bearer `, `basic ` and `ya29.`, lower-cased like the other starts; `Bearer` or `Basic` followed by white space (a tab too) and a non-space anywhere in a value, in any case (`Authorization: Bearer abc`), so `Basic plan` is refused too; and a scheme-less `user:pw@host` (a leading `mailto:` is dropped first, so `mailto:me@example.test` still reads). (4) **Names:** the whole words `pw`, `pswd`, `pin`, `totp`, `seed` and `mnemonic` (plural dropped like the others), and any word longer than 4 letters that ends in `pass` (`userpass`, `adminpass`, `mypass`). `passage` and `passive` still read. As a side effect `bypass` and `compass` are refused too; over-refusing is the safe side. Round 1 adds: (5) a number after a word is dropped before the word and `pass` checks (`key1`, `pass2`, `pw1`, `pin1`, `seed1`, `otp1`); (6) a word longer than `pw` (any longer word), `pswd` or `pin` (longer than 4 letters, so `spin` still reads) that ends in it is refused like the `pass` rule (`userpw`, `dbpw`, `dbpswd`, `userpswd`, `userpin`; `napkin` is not hit, a word such as `lupin` is, the safe side). (7) **Inside a URL (any `://`, also in the middle of a longer text):** the long-token test is applied to each path piece and each query or fragment value, and a query key, a `key=value` path piece or a path piece that names the next one (`/token/abc`) that is a secret word is refused. (8) **`name=value` inside a value:** a secret-looking name followed by `=` or `:` and a non-empty value is refused (`password=hunter2`, `api_key=abc123`, `token: abc`).
- **Options considered:** The issue's first pick, an allowlist of template keys, was dropped: it would have broken 13 existing tests that read keys not in the template, and the kit never rewrites a test to fit. A strict entropy test on values (more accurate, but needs a threshold nobody can defend). Refusing every long value (hides plain words and sentences; the letters-and-digits rule keeps `Cloudflare Workers` and plain words readable). The letters-and-digits rule does refuse a one-token value such as a dated model id (`claude-opus-4-5-20251101`), an ISO time (`2026-11-28T19:31:03Z`) or a path with a digit and no spaces; that is the safe side, and the template's model values are words with spaces, so no template key is hit.
- **Why:** A denylist always misses a format. One generic rule catches unknown key formats without a list. Over-refusing costs one "read the file yourself"; printing costs a leaked key. A generated set of 400,000 names and 400,000 values found none that the old lists refused and the new code lets through.
- **Originator:** AI pick, not reviewed (Full automation). The coordinator's scope-change comment on #740 set the four items; the exact rules, the port exception and the `mailto:` exception are the builder's.
