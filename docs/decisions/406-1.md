# Decision 406-1

- **Date:** 2026-11-28
- **Decision:** How #406 lines the review cap up with `routing`'s escalation, and the small CLI and `roles.mjs` follow-ups. (1) `coordinate`'s review cap on Full runs the extra round only if the builder has an escalation step left under `routing`'s "Escalation" (the profile's own limits win), and that round takes the step. With no step left, it goes straight to the split. It never moves a builder to the strongest tier on its own. `afk`'s On Full line for an issue that fails twice says the same. (2) An issue that can't be cut smaller gets its one new issue built on the same tier and effort as the last round: no escalation step is left by then, so "the next tier up" would be the third step `routing` forbids. (3) `routing`'s Escalation line now says the review cap follows it, instead of saying it overrides the cap, and decision 379-1's "until #406 lands" clause is done. (4) The README's line on what each pull request goes through says "one more round one step up if the builder has an escalation step left", since the step can be effort up, not a stronger model. (5) `npx onrails profile init` asks for the `fast` tier right after `everyday`, in the template's order, and the everyday question now names what that tier does in `routing` (the loop, reviews, big builds) instead of "building". (6) `npx onrails accounts` keeps "it never moves to another account" and adds the one exception from `routing`'s `references/accounts.md`, in its words: when you use Codex, non-security builds may go to ChatGPT; never to a second Claude account. (7) From the issue's comment, `roles.mjs`: a value with a C1 control (U+0080 to U+009F, NEL included) or U+2028/U+2029 can't be read, like C0 controls; `routing` set outside `[routing]` (a value or dotted key before any table, `[[routing]]`, `[routing.<name>]`) gets one warning that says that part is skipped and the `[routing]` table is still read; `roles.mjs <role>` resolves and warns about that role alone (profile-level warnings, which are about no single role, still print).
- **Options considered:** For (2), climb one tier from the last round with a cap at the tier below the strongest (more rules for the same outcome, since no step is left). For (5), ask for `fast` last, so the old test answers kept their order (the questions would no longer follow the template). For (6), reword to "never moves to another Claude account" (an existing test pins "never moves to another account", and `references/accounts.md` already uses the exception-then-never form). For (7)'s role filter, compute every role and drop the other warnings (more code for the same output).
- **Why:** One rule decides the extra round, `routing`'s, so the cap and the escalation can't disagree again. The wording copies the routing reference, so the CLI and the skill say the same thing.
- **Originator:** AI pick, not reviewed (Full automation: the owner, 2026-11-26). The rule that escalation never reaches the strongest tier on its own is the owner's, in #379.
