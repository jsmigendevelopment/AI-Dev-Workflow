# Decision 381-2

- **Date:** 2026-11-27
- **Decision:** How the weekly report reads the records, never estimating a number they don't hold. A run is a `job` record that ended (any outcome but `started` and `pr-opened`). A role comes from routing's table: `build` is the builder; `review-code`, `review-security` and `size-check` are the coordinator; any other job's role is `unknown`. A send-back is a record's `send_back`, or a `check` record with `state: failure`: the local gate's red run, which decision 380-1 records only that way, counts as `checks`. A send-back counts against the last build of the same pull request or issue at or before it, and against model `unknown` when there's none; "Per build" is send-backs over that model's builds this week. Size: no record holds a pull request's size, so the three buckets print `unknown`; the report names each pull request sent back for size (1,000 or more at that head) and gives the send-back rate over all pull requests (#427 records the size). An escalation is a build after a failed review or check (`review-must` or `checks`, a red gate included: routing's "verified failure") whose model or effort differs from the issue's build before it; `unknown` when either side's model or effort is. It counts any change, up or down, because routing's ladder isn't machine-readable: a step down or a renamed model counts too. It fixed it: among the issue's records after it and before the issue's next build on another model or effort (the next escalation, whose row those records belong to), the last failed review or check gives `no`, and a pass, a green gate (`check` with `state: success`) or a merge gives `yes`; none gives `unknown`. A retry on the same model and effort stays inside the row. Usage per merged pull request: a `merge` record in the week, over the build, review and qa runs on that pull request or its issue up to the merge; each run is its `usage_after` minus its `usage_before` when both are percentages and it didn't go down. It is the plan usage seen while those runs ran, not their cost: a plan reading covers the whole account, so it includes anything that ran beside them, and it reads low if the plan reset during a run (no record holds the reading's window or reset time yet, #431). Any run without both readings, or runs on more than one `tool` (two plans whose percentages don't add up), or two or more runs where any has no `tool` (it may be another plan), make it `unknown`. Two accounts on the same tool are still summed: no record names the account.
- **Options considered:** for size: count each head with `pr-size.mjs` from local git (its root is the script's own folder, so the CLI copy can't use it, and a head may not be in the checkout); read sizes from GitHub (the report only reads records); `unknown` until a record holds it, as above. For usage: read any number in the text (an estimate, against decision 380-2); a partial sum over the runs with readings (understates); percentages only, and `unknown` on any gap, as above.
- **Why:** The owner's rule: never estimate a number the records don't hold. Every rule above is a count or a difference of what a record says. A gap shows as `unknown`, so the report shows which readings to start recording.
