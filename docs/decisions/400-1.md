# Decision 400-1

- **Date:** 2026-11-27
- **Decision:** `check-issue-size.mjs` closes five gaps from the round 4 review of #391. (1) An exception whose reason names an issue (`#12`), or says it is split, fails as both an exception and a split. "Says it is split" means "split into", "splitting into", "split in two", "broken into", "already split", "was split", "Split.", "child issues" or "children 12 and 13". It passes only when a "no", "not", "never", "can't", "cannot", "won't", "don't", "unable", "without", "hard" or "too" sits in the same clause, right before the split ("can't be split into parts", "too risky to split up"). A clause ends at `, ; : . ( ) / – —`, a spaced dash, or "so", "and", "then" or "but", so "too big, split into child issues" and "too big - split into child issues" fail. (2) A later part of the value fails as a second estimate when one word or a `+` sits between its number and "lines" or "loc" ("+600 test lines", "600+ lines"), or when "test" or "tests" sits next to a number, also after a bracket, a dash, one qualifier or a word like "code" ("tests: 600", "tests: about 400", "tests (600)", "tests - 600", "test code: 600", "600 in tests"). A path ("test/12-x.ts", "x.test.mjs") or an ID ("AC-12-1 tests") isn't one. (3) A reason fails as a placeholder when it is "nope", "nothing", "later", "TBC", "no reason", "no reason yet", "no reason given", "not needed", "not applicable", "no need", "to be decided", "to be confirmed" or "unknown yet", or starts with "none", "tbd", "tbc", "todo" or "n/a" ("none yet", "TBD later"), except "none of ...". (4) The guard for a size the reader skips works as on main: the unit may follow the number anywhere in the same clause ("1,500 (est.) lines", "1,500 new code lines"). The one change is that a number with a size unit right after it (px, pt, em, rem, vh, vw, KB, MB, GB, TB, bytes) doesn't count, so "font size: 16px, line-height: 24px" passes. "about 300 lines changed" reads as 300. (5) On stdin, a split parent with no `labels` exits 2, and the exit 2 message names `labels`. (#400, review rounds 1 and 2 on #429)
- **Options considered:** for (1), fail any reason with "split" in it (refuses "no way to split a rename", a real reason the tests keep), only a reason that names an issue (misses "split into child issues"), or the split phrases above unless a negation comes first, looked for in the whole reason before it (round 0) or only in its clause, cut at punctuation alone (round 1) or also at a dash, a slash and "so", "and", "then" or "but". For (2), one word before the unit, or any words (refuses file lists). For (3), the exact phrases only, or a starting word too. For (4), the unit right after the number with a short word list between (round 0), any one word (round 1), or main's "anywhere in the clause" with the size-unit skip on the number. For (5), exit 2 for any issue with no labels (breaks older input that splits nothing), or only for a split parent.
- **Why:** Each choice fails the misuse the reviews found and keeps every real wording the tests and this repo's own issues use. Twice this line claimed the guard hid nothing main caught, and twice a review found shapes it hid (round 0: "1,500 code lines"; round 1: "1,500 (est.) lines"). So the promise now rests on a test, not on this line: `cli/test/issue-size-guard.test.mjs` lists every hidden size any review of #391 or #429 named and asserts each one fails next to a read Size line, and it lists every design note the size tests keep and asserts each one passes. A shape a later review finds goes into that list. A probe at round 2 also ran main's script and this one over 75 shapes from every review: none that main fails passes now. The wordings that pass where main failed are the ones #400 asks for: design notes with a size unit and "lines changed". All 30 real `Size:` issues in this repo read the same or better (#400's own body no longer trips the guard). The plan check imports this reader, so a step cell gets the same stricter rules.
