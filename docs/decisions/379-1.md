# Decision 379-1

- **Date:** 2026-11-27
- **Decision:** How #379 puts the owner's three roles into `routing`. (1) A new "Roles" section holds the owner's table (CTO on Fable 5.2 · high, coordinator on Opus 5.5 · medium, builder on Sonnet 5.5 · medium), and the Jobs rows name their role. Sonnet gets its own tier, **Fast**, so the Jobs table keeps speaking in tiers. (2) The profile override is real: `[routing]` in the profile template gets `cto`, `coordinator` and `builder` (the model) and `<role>_effort` lines, and `routing/scripts/roles.mjs` prints each role's model and effort, the project's `docs/profile.toml` first, then the home profile, per key, else the default. The tier lines stay notes, as AC-149-5 says. (3) "Big slices" means `Complexity:` 5 or more, the line where the old table moved builders to medium. (4) The escalation ladder: Sonnet · medium, Opus · medium, Opus · high; a builder that starts on Opus · medium goes to high, then extra-high where the model has it. After two steps, `coordinate`'s review cap decides; escalation never reaches the strongest tier on its own. The review cap in `coordinate` and `afk` still runs an extra round "on the next tier up", which after two steps would be a third step and can land on the strongest tier. Other pull requests are editing `coordinate`, so #406 changes both; until it lands, `routing`'s Escalation section wins and the issue goes straight to the split. (5) "Writing issues from the CTO's plan" moves to Strongest · high, the CTO row, as the owner's table says. The `issues` and `pyramid` skills still say issues are written on a cheaper model; they are outside this fence (#375, #376), so a follow-up issue aligns them. (6) The account rule: never move work between Claude accounts because of a limit; each app has a home account; when it's out, the app waits, or sends Codex-able work (non-security builds) to ChatGPT when the person uses Codex. `references/accounts.md` says the same. `cli/src/accounts.mjs`'s one-line rule is left as it is (outside the fence); #406 updates it and adds the `fast` question to `profile init`. (7) Security review keeps its job rule: one step above the code review. A role's effort is the base, and a job's own rule ("never below the builder", "one step above the code reviewer") raises it, so the coordinator's security review runs on Opus 5.5 · high. The Roles section says so, and the cheat sheet's example is Opus 5.5 high. (8) `roles.mjs` reads a profile only when it is a plain file; anything else gets one stderr line and falls through. It reads `[routing]` headers with spaces or a comment, quoted keys, basic strings with escapes and literal strings. A role or effort key it can't read, or an effort that isn't low, medium, high or extra-high, gets a stderr warning and the source says "could not read <key> in <file>".
- **Options considered:** One `cto = "model · effort"` string per role (harder to type and to parse than two plain keys); reading the tier lines as the override (AC-149-5 pins them as notes, and a tier isn't a role); a text-only rule with no script (nothing would check that the profile wins).
- **Why:** Plain keys are easy to set by hand, and the script gives agents and tests one place that decides. The test pins the script's defaults to the Roles table, so the two can't drift.
- **Originator:** AI pick, not reviewed (Full automation: the owner, 2026-11-26). The role table, the escalation rule, the account rule and the profile override are the owner's words in #379 and #374 (2026-11-27).
