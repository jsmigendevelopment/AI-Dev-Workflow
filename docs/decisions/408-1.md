# Decision 408-1

- **Date:** 2026-11-28
- **Decision:** How the merge gate checks `docs/insights/` and how `harvest` trusts a writer by user ID (#408). (1) `.gitattributes` marks only `docs/insights/*/*.json` `linguist-generated`, so a record file stays out of the size count and any other file there counts. (2) `pr-rules.mjs`, the one gate command that runs from main's checkout, reads each file the pull request leaves under `docs/insights/` (added, changed or renamed to; a removed file has nothing to check) at the exact head through the contents API, and applies `insights-land.mjs`'s own `recordProblem`, the check `land --verify` uses. A path that isn't a plain file or is over the 16 KB cap is named without its content being used. Each failing file is named with its reason: exit 1, `Checks: fail`. A file GitHub can't give is exit 2, never a pass. A records-only pull request from `land` passes, since each of its files is already one `land --verify` accepts; a build's own start and finish records pass the same way. (3) `harvest` trusts an account by its numeric user ID. gh's own ID comes from `gh api user` on every run; a writer is listed as `"login:id"` under `[insights] writers` in `docs/profile.toml`. The login is only a label: a comment whose ID is listed is kept even under a new login (a renamed writer), and one whose login matches gh's own or a writer's but whose ID doesn't is skipped and named with both IDs. A comment with no user ID is skipped and named. (4) A writer listed as a bare login is no longer trusted: `harvest` names the entry and says to list it as `"<login>:<id>"`, with the command that gives the ID. `land --verify` still compares the pull request author's login, as before; this issue only changes `harvest`.
- **Options considered:** For the check in the gate: a second record check in `pr-rules.mjs` (two rules to keep alike); fetch the head into main's checkout and run `land --verify`'s git diff (it needs the records-only pull request shape, which a normal pull request lacks, and the gate would run git on the head's objects); the contents API at the head with the shared `recordProblem` (picked: no head code or git object read, and `pr-size.mjs` already reads the head's content that way). For how a writer's ID is learned: resolve each listed login to an ID once per run with `gh api users/<login>` (no new profile format, but a login someone else took over after a rename would resolve to the new owner, so it adds nothing); resolve once and keep it in a cache file (a second place to go stale); store `login:id` in the profile (picked: the ID is pinned by the owner, so a renamed or recycled login can't fake it). For a bare login already in a profile: resolve it per run with a warning (keeps working, but leaves the hole open for that entry); refuse it and name the fix (picked).
- **Why:** The ID is the one thing about an account that a rename or a recycled login can't change, and only an ID the owner pinned in the profile is out of the reach of whoever takes a login over. The gate has to be the same check the records route uses, or a stray file under `docs/insights/` that `land --verify` would refuse could merge in a normal pull request, folded out of sight and out of the size count. Failing closed on a bare login costs one line in a profile, once, and the warning gives it.
- **Originator:** AI pick, not reviewed (Full automation: the owner, 2026-11-26). The ask is the issue's own words: "Narrow the attribute to `docs/insights/*/*.json`, and have the merge gate run the same record check `land --verify` uses on every changed file under `docs/insights/` in any PR", and "Compare the comment author's numeric ID with gh's own user ID, and let `writers` list IDs (or resolve each login to an ID once per run)."
