# Decision 538-1

- **Date:** 2026-11-28
- **Decision:** Preflight and doctor look at Go when the folder has a `go.mod` (#538). (1) Preflight's `CHECKS` stays the eight it was; a repo with a `go.mod` gets `go` ("Go toolchain") and `goproxy` ("Go module proxy") inserted before `model`, so a folder with no `go.mod` prints the same table and the existing tests stand. (2) The Go row runs `go version` and compares it with the `go` line of `go.mod`, read as data (a plain `1.N`, `1.N.P`, rc or beta; its `toolchain` line is never read). A Go older than that line, or no `go`, is blocked with its own ladder; a `go.mod` with no readable `go` line passes with the version shown. (3) The proxy row runs `go list -m -versions golang.org/x/sync` (one small module, asked only for its version list), then `go env GOPROXY` for the host it names, printed only when it is a plain host. It waits ("checked once go is installed and new enough") when the Go row isn't ok. (4) Both rows run `go` with `GOTOOLCHAIN=local`, from the empty temp folder outside the repo (the repo's own folder only after the read, and only when no such folder could be made), so go never fetches a toolchain, and reads no `go.work`, vendor folder or `toolchain` line of the repo's. They run before the read too, as the npm row does. (5) The proxy ladder's rung 1 is a project-local module cache (`GOMODCACHE="$PWD/.gomodcache" GOTOOLCHAIN=local go mod download`, with a PowerShell form on Windows) and a mirror in `GOPROXY`; rungs 2 to 4 follow the registry row's, with the proxy host. "Installs are blocked" now covers the `go` and `goproxy` rows. (6) `go.mod`'s `go` line goes into the sandbox fingerprint, and only when there is a `go.mod`, so no existing fingerprint moves. (7) `doctor` adds one check after pnpm when the project has a `go.mod`: `go version` run from the home folder by the same PATH search as every other tool (so a `go` in `node_modules/.bin` never runs), a fail with the install fix when `go` is missing or older than the `go` line, not required (the kit's own checks don't need Go). (8) `NO_AWAY` and `UNREAD` moved from `preflight.mjs` to `preflight-output.mjs` so the Go rows in `preflight-versions.mjs` use the same words; their text is unchanged. (9) Side effect (#566): `go list -m -versions` may create `pkg/mod` under the default GOPATH, even when the list fails, so preflight is not entirely write-free outside its temp folder. It is an empty folder, and `go mod download` was rejected because it fills the module cache.
- **Options considered:** Go rows always in `CHECKS` as "skip" with no `go.mod` (changes the table and fails `AC-100-1`'s "eight checks" test); a separate `preflight-go.mjs` (a new synced file for about 60 lines); `go mod download` as the proxy probe (writes the module cache, which is itself what a sandbox blocks); a `go.mod` module of the project's own as the probe (a name from the repo on a command line); doctor as a required check (a stray `go.mod` in a Node project would fail it).
- **Why:** The issue says a folder with no `go.mod` prints the same table, and the dossier (`research/go-api-toolchain.md`, #342) says the Go tools need Go 1.26.10 or newer, that `GOTOOLCHAIN=local` stops an automatic toolchain fetch, and that `GOMODCACHE` gets a project-local folder in the gate. `go list -m -versions` was run against an offline file proxy to confirm it works outside a module and exits 1 when the proxy can't answer.
- **Originator:** AI pick, not reviewed (Full automation). The issue gives the rows, the ladder and the doctor check; the probe module, the `GOTOOLCHAIN=local` rule, the doctor check being not required and where the code lives are the builder's picks.
