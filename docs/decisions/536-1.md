# Decision 536-1

- **Date:** 2026-11-28
- **Decision:** The docs that say `pnpm connect`, `wrangler` and `lib/env.ts` get a Go service's form beside them (#536), on the host and database decision 340-1 picked (Google Cloud Run, Neon) and the push script decision 537-1 made (`push-secrets.mjs --cloud-run`). (1) `guide/environments.md` adds a "Go service" form to each example that names `pnpm deploy:test`, `wrangler`, a Zod schema or `lib/env.ts`, and links section 16 of `guide/app-conventions-go.md` instead of repeating it; it stays under 200 lines. (2) A Go service has no `pnpm connect`: the person signs in with `gcloud auth login` in their own terminal and pastes each value into a git-ignored `.env.test.local` or `.env.production.local`, and the agent runs `push-secrets.mjs --cloud-run`, dry first. Check by name is `push-secrets.mjs --dry-run --cloud-run` (each empty value, and where it would go) and `gcloud secrets list` (Secret Manager's names). (3) Two new provider files, `cloud-run.md` and `neon.md`, each with a `json connect` block (the existing `connect-blocks` test needs one in every file but Supabase's). The blocks fill only names no web pack or add-on lists (`CLOUD_RUN_PROJECT`, `CLOUD_RUN_REGION`, `NEON_PROJECT_ID`, all public) and walk at order 70, after every web provider, so `pnpm connect` in a web app never asks for them and the web walk order is unchanged. `DATABASE_URL` is not in a block: the Supabase add-on lists the same name, and a block that filled it would make a Supabase web app walk Neon. `NEON_API_KEY` is not in a block either: `keys-on-full.test.mjs` pins the number of secret rows at 15, and a test that no pull request may change to pass would turn red on a sixteenth; the walkthrough still tells the person to make the key and keep it in their own shell. (4) `clerk.md` gets a "Go backend" paragraph: `CLERK_SECRET_KEY` for the Go service, through Secret Manager; the origins list's name and the SDK-or-fallback choice are left to the Go pack's sign-in step. (5) `cli/test/go-environments.test.mjs` guards the above, including that the walk order of the web providers is the one on main.
- **Options considered:** the Go form in a separate `guide/environments-go.md` (the issue says each example gets its form beside it, and the file stays under 200 lines); no new provider files and `NO_BLOCK` in the existing test gaining two names (it changes an existing test, which no pull request may do to pass); a block that fills `DATABASE_URL` (changes a Supabase web app's walk); one provider file for both Google Cloud and Neon (a person signs in to each separately, so each is its own walkthrough, as the web providers are); naming the Cloud Run deploy variables as picked (the Go pack's deploy script is not on main).
- **Why:** The owner's words in #279 make the Go service the default for an app that needs a backend and outgrows Workers, so the first test deploy of such an app reaches the `secrets` skill, which named only `wrangler` and `gh`. Putting the Go form beside each Workers example keeps each rule in one place. Picks that nothing on main had made are the builder's, and the files say which: `CLOUD_RUN_PROJECT`, `CLOUD_RUN_REGION`, `NEON_PROJECT_ID` and `NEON_API_KEY` as names (the Go pack's own `.env.example` and deploy script, not on main, may choose others); test and production as two Neon projects, as the Supabase file does for its two; a preview using the test values until the deploy script says otherwise; `gcloud auth list`, `gcloud secrets list`, `neon auth` and `NEON_API_KEY` as the commands and variable, which come from the vendors' usual CLI shape and were not run (marked `[U]` in the files). Not run: no real `gcloud`, Neon CLI or account was used.
- **Originator:** AI pick, not reviewed (Full automation). The issue gives the files and the lines; the names, the order 70, the connect blocks' variables, the two-project split and the check-by-name commands are the builder's picks.
