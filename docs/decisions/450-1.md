# Decision 450-1

- **Date:** 2026-11-28
- **Decision:** The open choices in #450, each the recommended pick. (1) Carry's fetch keeps `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` and still drops `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM`. Its `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c core.attributesFile=/dev/null` flags come after the environment's config, so they win (checked with git 2.43: the last value of a key is the one used). Carry's other git calls still drop every `GIT_` variable, as they run no remote command. This replaces the clause in decision 333-2 that says carry's fetch of main drops config given through the environment (`GIT_CONFIG_*`); the rest of 333-2 stands. (2) Land's checkout is found by `checkoutAt()`, which runs `git rev-parse --show-toplevel` with land's own env (`gitEnv()`), not by carry's `checkoutOf()`. `gitRoot()` in `insights.mjs` calls it, so it covers every command that uses `gitRoot()` (`write`, `harvest`, `has-records`, `land`), and the start folder is still `CLAUDE_PROJECT_DIR` or the current folder (decision 490-1 keeps that for them). (3) Carry's fetch gets no `--no-tags`: #450 names land's fetch only, so a tag on the remote can still be auto-followed into the coordinator's checkout when carry fetches main. (4) Land's pull request check (`land --verify`) fetches with `--no-tags` too, since it is one of land's fetches. (5) What land keeps and drops, and how it differs from carry's fetch, is in decision 422-1, the record #450's item 4 asks for.
- **Options considered:** For (2): reuse `checkoutOf()` for land, as the brief hinted. It is isolated (no `GIT_` variable, `GIT_CONFIG_GLOBAL=/dev/null`, `HOME` in a temp folder), but it runs from the script's own folder in carry's case and loses the global `safe.directory` in any case, so a checkout owned by another user (a dev container's mounted folder) would fail before land's own calls, which keep the global config, could run; land's `gitEnv()` has neither problem. Move the checkout to the script's own folder like carry (#490): `harvest` writes into the checkout `gitRoot()` finds, so land would stage from a different one. A comment only, saying the guarantee starts once the checkout is found: leaves `GIT_DIR` able to move land. For (1): keep dropping every `GIT_CONFIG_*`, the old behaviour, which loses the rewrite; keep all of them, including `GIT_CONFIG_GLOBAL`, which the issue doesn't ask for and which would let a hook name the config file the fetch reads. For (3): add `--no-tags` to carry's fetch too, which the issue leaves out and which changes carry's checkout for no reported bug; follow-up if wanted.
- **Why:** The brief says the isolation guarantees (no hooks, no global config, main's attributes only) stay as they are, and these picks change only what the issue lists. The fetch is the one call that talks to a remote, so it is the one that needs the environment's rewrite; the calls that merge stay fully isolated.
