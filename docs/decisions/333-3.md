# Decision 333-3

- **Date:** 2026-11-27
- **Decision:** `has-records` counts any `job` record with the pull request's number and the head sha, whichever job wrote it. In practice that is the reviewer's `job=review-code` line, or `carry`'s `job=carry-review` (decision 333-2): the builder's finish record names the commit before it and sits on the branch, not in the coordinator's checkout. It counts a file only when `land` would land it as it is (`recordProblem`: a `docs/insights/<yyyy-mm-dd>/` path of the record's own day, the writer's exact bytes and the name that matches it), and never a `source: board` record. It checks presence, not pass: the verdicts are the `Checks:` comment's and the review's. A file that fails counts as missing; a checkout it can't read exits 2. (#333)
- **Options considered:** only `job=review-code`, which would also refuse a carried review and a head whose review line was lost after `qa` or the security review ran, and gives the same answer in every other case; any `job` record that passes `validate`, the first pick here, which counted files `land` leaves out, so a merge could go ahead and main never get the record; any `job` record that `land` would land
- **Why:** The check exists so main ends up with the records. Using `land`'s own rule means a record that counts is a record that lands. Board records skip the kind's fields, so once board events become records (#346) one could stand in for the reviewer's line.
