# Decision 333-2

- **Date:** 2026-11-27
- **Decision:** When the coordinator merges main into a reviewed branch whose base is behind (`coordinate` step 7), `insights.mjs carry --pr <n> --from <reviewed sha> --to <merge sha>` carries the review to the merge commit. It passes only when the merge commit has exactly two parents, the first is the reviewed sha, the second is on `refs/remotes/origin/main` (fetched with an explicit refspec, never read by the short name `origin/main`, which a tag or a local branch can shadow), a merge of the two has no conflict and gives exactly the merge commit's tree, and the reviewed sha has its job and review records. The merge is `git merge-tree --write-tree`; a git before 2.38 has no `--write-tree`, so carry merges in a throwaway clone in TMPDIR that borrows the checkout's objects (`clone --shared`) and changes none of its refs, index or files, and old git carries the same as new git. **Every** review record for that pull request at the reviewed sha must have `verdict: pass`, and every `review-code` or `carry-review` job there `outcome: pass`, not only the latest; a review or review job already at the merge sha that didn't pass also refuses. Then it writes a `job` record (`job=carry-review`, `outcome=pass`) and a copy of the latest review, both at the merge sha, through the writer. Anything else exits 1, and the merge commit goes to a fresh `pr-review`. When `carry` exits 0, the old head's `qa` and security verdicts stand for the merge commit too, as they did before #333 for a merge with no conflict fix; step 6's "A verdict stands until the commit changes" says so. Exit 2 (usually a branch not fetched yet): fetch it and run `carry` once more in the same step; a second exit 2 on the same merge sha goes to a fresh `pr-review`, with one ℹ️ FYI, so nothing retries forever. The gate (step 6.1) still runs on the merge commit and writes its own `check` record. Every git call in `carry` is isolated, as `pr-size.mjs`'s is (#225): no `GIT_` or token variable (a hook's exported `GIT_DIR` or `GIT_INDEX_FILE` would point the redo at the coordinator's checkout), `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_ATTR_NOSYSTEM=1`, `HOME` and `XDG_CONFIG_HOME` at the temp folder, and `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c core.attributesFile=/dev/null`, so a global `pull.twohead`, merge driver or relative `hooksPath` can't change the merge. The one fetch of main drops only the variables that move the repository (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE`, `GIT_CEILING_DIRECTORIES`, `GIT_COMMON_DIR`) and config given through the environment (`GIT_CONFIG_*`), sets `GIT_TERMINAL_PROMPT=0` and passes the same `-c` flags, but keeps `HOME`, the global config, tokens and transport variables, because its login lives there; it merges nothing. Every isolated call also gets `-c safe.directory=<checkout root>`, since a `safe.directory` in the dropped global config would be ignored. The merge always uses main's merge attributes, never the branch's: on new git `merge-tree` reads the checkout's (main's) `.gitattributes`, and the old-git redo writes `* merge=text` and then the checkout's own `.gitattributes` into the clone's `.git/info/attributes`, which outranks every `.gitattributes` in the tree. So a pull request that edits a `.gitattributes` carries on every merge of main, and a merge attribute only on the branch can't make its own merge clean. The temp folder is removed on exit and on SIGHUP, SIGINT or SIGTERM. (#333, review rounds 1 to 4 on #413)
- **Options considered:** a fresh `pr-review` for every merge of main, the first pick here, which stalls the loop: step 10 lands a records pull request most sweeps, so main moves every sweep, a branch behind it waits on a separate review agent that usually returns after main has moved again, and every code merge costs each queued pull request one more review (reviews grow with the square of the queue); keep the fresh review but have step 10 skip `land` while a code pull request waits on one, which slows records and keeps the extra reviews; a script that proves a clean merge of main and carries the review. For which reviews count: only the latest, which lets a later pass outvote a `changes` from a second review the dial added at the same sha; every review at the sha, picked, since a fix for a `changes` verdict is a new commit with its own review anyway. For a git before 2.38: send every merge of main to a fresh review, which is the first option's stall again on that git; skip `land` while such a review waits and ask for git 2.38, which slows records and needs the person; redo the merge in a throwaway clone, picked, since a plain merge works on any git. For merge attributes: refuse whenever a `.gitattributes` differs between the two sides, the round 4 pick, which a pull request that edits a `.gitattributes` hits on every merge of main, so it stalls as the first option does (not needed on new git, where `merge-tree` already reads main's); refuse only in the old-git redo, which still stalls such a pull request on old git; main's attributes in the clone's `.git/info/attributes`, picked, since old git then carries the same as new git. Only main's top-level `.gitattributes` goes there: a merge rule in one of main's nested `.gitattributes` files is overridden by `* merge=text` in the redo, so such a merge may conflict there and go to a fresh review, which fails safe.
- **Why:** Every record is still written by a script with the exact merged head sha (#281 AC-1), and `has-records` stays exact (AC-333-2). A conflict fix or any change of the coordinator's own still gets a fresh review, and only a passing review carries, so a rejected head's merge commit can't pass the record check. A clean merge of main costs no review, no `qa` and no security review, as before #333, on any git, so the loop never stalls on main moving.
