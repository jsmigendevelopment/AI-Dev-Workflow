# Decision 333-2

- **Date:** 2026-11-27
- **Decision:** When the coordinator merges main into a reviewed branch whose base is behind (`coordinate` step 7), `insights.mjs carry --pr <n> --from <reviewed sha> --to <merge sha>` carries the review to the merge commit. It passes only when the merge commit has exactly two parents, the first is the reviewed sha, the second is on `refs/remotes/origin/main` (fetched with an explicit refspec, never read by the short name `origin/main`, which a tag or a local branch can shadow), `git merge-tree --write-tree` of the two has no conflict and gives exactly the merge commit's tree, and the reviewed sha has its job and review records. **Every** review record for that pull request at the reviewed sha must have `verdict: pass`, and every `review-code` or `carry-review` job there `outcome: pass`, not only the latest. Then it writes a `job` record (`job=carry-review`, `outcome=pass`) and a copy of the latest review, both at the merge sha, through the writer. Anything else exits 1, and the merge commit goes to a fresh `pr-review`. So does a git too old to prove the merge (`--write-tree` needs 2.38). In step 7, a second exit 2 on the same merge sha also goes to a fresh `pr-review`, with one ℹ️ FYI, so nothing retries forever. The gate (step 6.1) still runs on the merge commit and writes its own `check` record. (#333, review rounds 1 and 2 on #413)
- **Options considered:** a fresh `pr-review` for every merge of main, the first pick here, which stalls the loop: step 10 lands a records pull request most sweeps, so main moves every sweep, a branch behind it waits on a separate review agent that usually returns after main has moved again, and every code merge costs each queued pull request one more review (reviews grow with the square of the queue); keep the fresh review but have step 10 skip `land` while a code pull request waits on one, which slows records and keeps the extra reviews; a script that proves a clean merge of main and carries the review. For which reviews count: only the latest, which lets a later pass outvote a `changes` from a second review the dial added at the same sha; every review at the sha, picked, since a fix for a `changes` verdict is a new commit with its own review anyway.
- **Why:** Every record is still written by a script with the exact merged head sha (#281 AC-1), and `has-records` stays exact (AC-333-2). A conflict fix or any change of the coordinator's own still gets a fresh review, and only a passing review carries, so a rejected head's merge commit can't pass the record check. A clean merge of main costs no review, as before #333, so the loop never stalls on main moving.
- **Not covered here:** in the kit's own repo the reviewer runs the checks (decision 28) and writes no `check` record, so `has-records` sends each kit pull request back to step 6.1 for a second check run: follow-up #417. `insights-land.mjs` (#332) still reads main by its short name in three places: follow-up #422.
