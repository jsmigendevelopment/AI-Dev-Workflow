# Decision 537-1

- **Date:** 2026-11-28
- **Decision:** `push-secrets.mjs` gets a destination for a Go service's host, Google Cloud Run (decision 340-1), as the flag `--cloud-run` next to `--wrangler` (#537). (1) A secret goes to Secret Manager as `<base>-<env>-<NAME>`: `gcloud secrets create <id> --data-file=-`, and when that fails (the secret exists) `gcloud secrets versions add <id> --data-file=-`, the value on stdin. (2) A plain variable goes to the service `<base>-<env>`: `gcloud run services update <service> --flags-file=<temp file> --quiet`, the file holding `{"--update-env-vars": {"NAME": "value"}}` (JSON is YAML), made mode 600 in a fresh temp folder and deleted after the call, so no value is ever an argument. (3) `<base>` is `api` unless `--service BASE` says; `--region` and `--project` pass through to gcloud; all three must be plain lowercase names or the script exits 1 before any call. Every gcloud call gets `--quiet`, so a prompt can never read the value off stdin. (4) A name takes one gcloud call (a secret that already exists takes a second one, the new version); a call that could not start gcloud (not on PATH) is not retried. (5) The failure rules are `--wrangler`'s: a `FAILED` line (values hidden), exit 1, and the last line says "Stored nowhere" or "Not stored everywhere". A secret refused by both create and add shows both reasons. (6) The script does not wire a secret into the service: that is the deploy's `--update-secrets NAME=<id>:latest`, which the Go pack sets on every deploy (decision 340-1). (7) In a repo with a `go.mod` in the app's folder or any folder above it up to `.git`, push-secrets' `ci = "local"` line and its "stored nowhere" reasons name `--cloud-run`, and `setup-github`'s closing line says "push-secrets --cloud-run for the Go service, --wrangler for a web app on Cloudflare"; without a `go.mod` every message is as before. (8) The new tests are in `cli/test/push-secrets-cloud-run.test.mjs` and `cli/test/ci-local-secrets.test.mjs`; `push-secrets.test.mjs` and `push-secrets-scrub.test.mjs` are untouched. `cli/test/secrets-fakes.mjs` gains a fake `gcloud` and logs the contents of a `--flags-file`, which no existing test reads.
- **Options considered:** one flag per host service (`--secret-manager`, `--cloud-run-env`); `--update-env-vars=NAME=value` for a plain variable (a value in an argument, which AC-537-2 forbids); `--env-vars-file` (replaces every variable of the service, so one name would wipe the others); `gcloud secrets describe` first, then create or add (a second call for every name); trying `versions add` first (one call for a rotation, but a failed first push reports a misleading error); wiring each secret into the service with `--update-secrets` (a new revision per name, and the deploy owns it); a required `--service` (the "Try it" line runs with the flag alone).
- **Why:** The commands are in Google's reference: `gcloud secrets create SECRET --data-file=-` reads the value from stdin and errors if the secret exists; `gcloud secrets versions add SECRET --data-file=-` adds a version to an existing one; `gcloud run services update SERVICE --update-env-vars` changes one variable and keeps the rest; `--quiet` and `--flags-file=YAML_FILE` are global gcloud flags, and a dictionary flag is a YAML mapping in the file (`gcloud topic flags-file`). The mapping form for `--update-env-vars` is read from that topic, not run against a live service (no real gcloud runs in tests, and none was run here). Windows `gcloud.cmd` takes only plain words, so a temp folder with a space in its path makes a plain variable's call refuse with a `FAILED` line.
- **Originator:** AI pick, not reviewed (Full automation). The issue gives the flag's job, the hiding rule and the messages; the flag name `--cloud-run`, the default base `api`, the `<base>-<env>` and `<base>-<env>-<NAME>` names, create-then-add, the flags file for plain variables, `--service`, `--region` and `--project`, leaving the wiring to the deploy and the go.mod lookup are the builder's picks.
