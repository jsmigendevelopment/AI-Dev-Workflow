# Decision 707-1

- **Date:** 2026-11-28
- **Decision:** In the TanStack Start pack's `eslint.config.js`, `boundaries/dependencies` refuses a `*.service.ts` file importing another `*.service.ts` file ("a controller composes services"), and a repository file importing another repository file ("a service composes repositories"). The repository files are two file categories, `repository-port` (`*.repository.ts`) and `repository-adapter` (`*.repository.drizzle.ts`, `*.repository.memory.ts`), each capturing the base name. One exception: an adapter may import the port with the same base name. An adapter importing another adapter, a port importing an adapter, anything importing a repository of another name, and an adapter importing the same-named port of another module are refused. Controllers get no new category: they may import services, as before.
- **Options considered:** (1) Refuse every repository-to-repository import, with no exception: an adapter could not implement its own port, so the example module would fail. (2) Allow any repository import that has the same base name: an adapter importing its sibling adapter would pass. (3) Allow only an adapter importing the port of its own name: the narrowest exception that keeps `notes.repository.drizzle.ts` and `notes.repository.memory.ts` valid.
- **Why:** The issue says same-name adapter to port stays allowed; (3) keeps exactly that and refuses the rest, so the lint only catches more. The policy list is "last match decides", so the exception sits after the two refusals and matches the target's captured `module` and `name` against the importing file's (name alone let an adapter reach a same-named port in another module, which the module policy refused before; found in review of #717). Each probe in `scripts/lint/lint-rules.test.ts` goes through the real config.
