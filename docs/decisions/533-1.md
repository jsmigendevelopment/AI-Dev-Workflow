# Decision 533-1

- **Date:** 2026-11-28
- **Decision:** The Go backend's code style is one new guide, `guide/code-style-go.md`, that mirrors the rules of `guide/code-style.md` that name a TypeScript tool and keeps their numbers: 3, 4, 14 and 15, plus 5, 11 and 12, which name no tool but which `AGENTS.md`'s Code rules and the reviewer compare across both guides. Each section has the rule, a short Go example, a "Kept by" line and a "Why" line. (1) Rule 4 bans `any` and `interface{}` in an exported signature and a bare `//nolint`; a `//nolint` carries a linter name, a reason and an issue number. (2) Rule 14 gives Go file and package naming (no `util`, no `init()` that does work, no re-export package, three import blocks, the full module path in place of an alias). (3) Rule 15 points money, time, logs, events, env and access at the packages in `guide/app-conventions-go.md`, and does not repeat them. (4) The tools are only the picks of decision 342-1: golangci-lint with depguard, funlen at 60, nolintlint and revive's `file-length-limit` at 500, `scripts/check-file-size.mjs` for the 300-line warning and the `#<issue>` check, go-arch-lint, `internal/` folders, `gofmt`, `go vet` and `go mod tidy -diff`. Where no pick checks a rule (an `any` in a signature, an ignored error, `fmt.Print*`, `time.Now()`, `init()`, `util` names), the guide says so and leaves it to `pr-review` by hand; it names no linter the dossier did not pick. (5) The guide names no version. (6) `AGENTS.md` gets two edits and nothing else: the escape-hatch rule adds "or the stack's equivalent (`//nolint` in Go)", and the barrel rule adds "or the stack's equivalent (in Go, a package that only re-exports)". (7) The guide is not copied into `build/references`, like decision 348-1; `code-style.md` gains one pointer line, and its copy follows by sync.
- **Options considered:** section layout: a section per rule with the original numbers, new Go-only numbers, one table only; which rules to cover: only the four that name a TypeScript tool, those four plus 5, 11 and 12; the barrel line's wording: the issue's literal "(`//nolint` in Go)" on both lines, a Go equivalent that fits each line; a rule with no linter in the picks: name a real linter the dossier did not test (`errcheck`, `forbidigo`), say that nothing checks it yet; the Go guide copied into `build/references`, linked only from the guide index and `code-style.md`.
- **Why:** Keeping the numbers makes "rule 4" mean the same in both guides, so a review can compare them side by side (as decision 348-1 did for the conventions). The issue's acceptance check 5 compares file size, no empty catch and comments-say-why across both guides, so 5, 11 and 12 get a Go section even though they name no tool. The issue gives one phrase for both `AGENTS.md` lines, but `//nolint` does not excuse a barrel file, so the barrel line names what is the equivalent in Go: a package that only re-exports another's names (the issue's acceptance check 4 still gets a Go equivalent on both lines). The issue calls them lines 57 and 60; on current main they are lines 58 and 61, so the test finds each by what it says, not by number. The brief says to pin only what the dossier pins and never to invent a tool, so a gap is named as a gap: it tells the person what review still has to read, and the Go pack's lint config (#349, #350) can fill it. The guide stays at about 150 lines, under the issue's 300. Confidence: medium. The "Kept by" lines are the most likely to change when the Go pack's lint config lands.
