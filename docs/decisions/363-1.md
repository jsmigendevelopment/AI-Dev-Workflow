# Decision 363-1

- **Date:** 2026-11-28
- **Decision:** Two edits to `coordinate`'s Rules, nothing else in the skills (#363). (1) The usage-limit rule gains one sentence: at the limit, write a one-line resume note to `docs/state.md` (or the live thread) with what is in flight, so the restart message isn't stale. (2) A new rule, "After a usage-limit reset", beside it: before picking new work, read that note, list this session's child sessions, send each one whose last turn failed a message to carry on its brief, or start a fresh one if it can't resume. `cli/test/limit-resume.test.mjs` pins both in the master and in each synced copy. `ask` is unchanged: its resume note is the one for `pause` and `stop`, not for a limit.
- **Options considered:** Put the reset steps inside the existing usage-limit line (it is already long, and `supervisor.test.mjs` pins its sentences, so a second rule keeps those untouched), or add a step to the loop's sweep (a limit is an event, not a sweep step, and the rule list is where `coordinate` already keeps it). Write the note only to `docs/state.md` (the live thread may be the only place a cloud loop can write), or only to the thread (a new session reads the repo, not the thread). The issue allows either, so the rule names both.
- **Why:** The rule is short, tool-neutral (no tool name for listing sessions) and gives no way to move work to another account, which stays out of scope. Reading the note first lets the loop name what the restart message got wrong.
- **Originator:** AI pick, not reviewed (Full automation). The picks are: a separate rule beside the usage-limit rule, the order (read the note, list the children, resume, then new work), tool-neutral wording, and leaving `ask` alone.
