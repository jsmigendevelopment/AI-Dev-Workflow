# Decision 441-1

- **Date:** 2026-11-28
- **Decision:** Which comments `insights.mjs harvest` keeps a `check` line from (#441). (1) A `check` record is kept only from a comment that reports the run, and only when the comment says the same thing the record does: its verdict names the record's `sha`, and `Checks: pass` goes with `state: success`, `Checks: fail` with `state: failure`. (2) Two comment shapes report a run, both copied from the loop's real comments (#523, #524, #525, #510): the merge helper's, whose first line is `Checks: pass|fail @ <sha>`; and the reviewer's one verdict comment, whose first line is `Code review: approve|request changes @ <sha>` and which holds exactly one `Checks: pass|fail @ <sha>` at the start of a later line, with the same sha as that first line. (3) Anything else is skipped and named on stderr (`skipped a line in comment <id> by <login>: check line: <why>`), and harvest still exits 0. The other kinds, and every other rule (trust by user ID, pr number, valid record), are unchanged. (4) The `Checks:` line inside the reviewer's comment must start its line, so a quoted or indented copy doesn't count. Two such lines make the comment unclear, so the check line is skipped. (5) `references/insights.md` says the rule and, as the coordinator asked on #441, that the reviewer's `fence` holds only the fence's name while the gate's own record keeps the whole `Fence:` line.
- **Options considered:** (a) The issue's words, literally: the comment's first line is `Checks: pass|fail @ <sha>`, nothing else. The loop's reviewers put `Code review: approve @ <sha>` first and the `Checks:` line near the end, so every reviewer's check line would be skipped. Then `has-records` would find no check record, and the merge step would run the local gate again for every pull request (or hold it). Rejected. (b) The first line is `Checks:` or `Code review:`, and the `Checks:` verdict can be anywhere in the comment, including mid-line or quoted. Simpler, but a line like `> Checks: pass @ <sha>` quoted in a builder's note would count. Rejected. (c) What this does: the two shapes above, with the verdict at the start of a line. Chosen. (d) Ask pr-review to post a separate `Checks:` comment for the check line. Keeps the issue's rule literal, but it changes the reviewers' format, doubles their comments, and touches `pr-review` and its tests, which the issue's fence doesn't name. Not now.
- **Why:** The rule's purpose is that a stray line elsewhere can't stand in for the run. Both shapes are the only places the loop writes a run's verdict, and each names the sha and the result in a place a builder's note doesn't write them. Reading the issue's first-line rule only literally would break `has-records` for the whole loop, which the issue didn't intend. This stays inside the issue's modules: `insights.mjs`, its reference and a test in `cli/test/`.
- **Originator:** AI pick, not reviewed (Full automation: the owner, 2026-11-26). The ask is the issue's own words: "harvest keeps a `check` line only from a comment whose first line is `Checks: pass @ <sha>` or `Checks: fail @ <sha>`", read so the reviewer's verdict comment, whose first line is `Code review: ...`, still counts.
