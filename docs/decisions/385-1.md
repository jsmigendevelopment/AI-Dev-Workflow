# Decision 385-1

- **Date:** 2026-11-27
- **Decision:** How `lesson check --project` reads joined names and issue numbers (#385), on top of decision 322-1.
  - **Whole terms:** a term kept whole (an `.env.example` variable name, a full host) now also gives its parts joined by a space and by a hyphen, but still not its parts alone. `RIVER_SIGNAL_TOKEN` gives `river-signal-token` and `river signal token`, never `river` or `signal`.
  - **Split and joined forms:** every term is also compared with its spaces and hyphens removed against a run of two or more lesson words with theirs removed, in either number. So `bright paper` and `bright-paper` match `brightpaper`, `river-signal token` and `river signal-token` match `RIVER_SIGNAL_TOKEN`, and `river signal key` matches `RIVERSIGNAL_KEY`. A word alone never does, so `paper` still passes. A field over 2,000 characters skips this scan, so a huge field stays fast; `lesson check` refuses any such field for its length anyway.
  - **Issue numbers:** with a project (always, in the CLI, since `--project` defaults to the current repo), `issue <n>`, `PR <n>`, `pull <n>` and `pull request <n>`, plural or not and with an optional `number` or `no` before the number, are refused for any number, as `field: contains a project term (issue number)`. A number followed by `times` or `x` is a count, not an issue, so `the same issue 3 times` passes. `#<n>` was already refused by #321's sentence rules. The number is never printed.
  - **The list of words** stops at the ones GitHub uses for issues and pull requests (`issue`, `PR`, `pull`, `pull request`). Other words such as `ticket`, `change`, `bug` or `step` name other things just as often (`change 2 files`, `step 3`). Adding them would refuse ordinary counts, and #321 already refuses any run of three digits.
  - **Lesson file size:** a lesson file over 1 MB is refused before it is read, as `record: too-large`.
- **Options considered:**
  - Joined names: split a joined name into dictionary words when the set is built (needs a word list, and a name can split more than one way); join the lesson's words for one-word terms only (misses a mixed form such as `river-signal token`); or compare every term and every run of words with spaces and hyphens removed.
  - Env names: keep them whole as 322-1 says; split them into parts (blocks `key`, `secret`, `token`); or keep them whole plus their spaced form.
  - Issue numbers: refuse them only when the number shows up in the project's files (misses an issue the docs never name), or for any number when a project is checked. Words: GitHub's own, or also `ticket`, `change` and `bug`. Counts: refuse `issue 3 times` too, or let a number before `times` or `x` pass.
  - Where the issue check runs: inside the term matcher, or next to it in `lesson-check.mjs`. It needs no deny set, so a project with no terms still refuses it.
  - `#<n>`: refuse it twice, or leave it to #321's rule.
  - A long field: no limit, cap the scan, or cap the lesson file. This does both: the file at 1 MB, the scan at 2,000 characters.
- **Why:** Privacy first, and the false refusals stay where they were. The test app was made with `init` and `add tanstack-start`, with its own made-up docs. On main and on this change, 2 of 42 clean kit-style lessons are refused, both for `start` (from TanStack Start in the docs). 8 of 3,939 common words are refused on both. The one new refusal is the phrase `security contact`, from the pack's own `SECURITY_CONTACT` in `.env.example` (#410). A kit lesson is about the kit, so a project's issue numbers carry nothing a lesson needs.
