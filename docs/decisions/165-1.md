# Decision 165-1

- **Date:** 2026-11-27
- **Decision:** How #165 stops decision rows clashing between parallel pull requests. Each new decision is its own file, `docs/decisions/<issue>-<n>.md`, and its id is the file name (`165-1`). The rows already in the table in `docs/decisions.md` stay with their numbers, and the table takes no new rows. An end marker, `<!-- decisions-table-end -->`, sits just after the last row, after one blank line, and is the file's last line. The table is capped: `LAST_TABLE_ROW` in the test is main's last row when this merges (118: #273 and #270 landed first), and the ids must be exactly 1 to `LAST_TABLE_ROW`, in order. A row added anywhere, right after the last row or below the marker, fails with "No new table rows after #165: record it as `docs/decisions/<issue>-<n>.md` and cite it as `decision <issue>-<n>`." An open pull request that still adds a row (#270) fails the same way and moves its decision to a file. The cap is never raised to let a new row in. A replaced decision is found by `grep -rnE "Replaces decision <id>([^-0-9]|$)" docs/decisions.md docs/decisions/`, which also reads the table and doesn't take `43-1` for `43`; rule 16 says a replaced row or file lifts nothing, and a file in `docs/decisions/` counts as a row. A changed decision is a new file that says `Replaces decision <id>`; the old one isn't edited. In an app, the kickoff (one session) still writes table rows; after it, every decision is a file. `cli/test/decision-ids.test.mjs` merges two branches that each add one with plain `git merge`, checks the table's ids are exactly 1 to `LAST_TABLE_ROW` and that a row appended right after the last one fails with that message, and checks every `decision <id>` cite in the kit's skills, scripts, tests, docs and changelog resolves.
- **Options considered:** ids `<issue>-<n>` as rows in the same table; rows numbered only at merge by a script; keep numbers and a renumber script; one file per decision. For the freeze: a floor (ids 1 to N with no gap, at least to the last row), which let a row appended after the last one pass (round 2 review); a named list of grandfathered rows for open pull requests; an exact cap
- **Why:** Ids that can't clash still conflict as text when two branches append a row at the same end of the table, and GitHub's merge ignores custom merge drivers. A file per decision touches no shared line, so both merge with no step at merge time and no renumbering. Editing the old row to note a replacement would touch shared lines again, so the new file names what it replaces. An exact cap is the one freeze that fails a row in the place agents add one, and its message says where the decision goes; a grandfather list would still need an exact end.
