# Decision 476-1

- **Date:** 2026-11-28
- **Decision:** `readRouting` in `roles.mjs` reads `["routing"]` and `['routing']` (optional spaces inside the brackets, optional trailing comment) as the `[routing]` table. Only `HEADER` changed: it now accepts `routing`, `"routing"` or `'routing'` between the brackets, each as a whole form. `OTHER_ROUTING` is unchanged, so `[[routing]]`, `[routing.<name>]` and their quoted forms still set `misplaced` and warn. A quoted key with anything else in it (`["routing.x"]`, `["routing_notes"]`, `["other"]`, a mismatched `["routing']`) is still another table, and its keys are still skipped, as before.
- **Options considered:** (1) Read the quoted single-table forms as `[routing]`. (2) Flag them as `misplaced`, so the existing warning names them and the keys stay skipped. (3) Leave them as they are (the bug: skipped, no warning).
- **Why:** TOML says `["routing"]`, `['routing']` and `[routing]` name the same table, so the person's keys mean what they wrote. Option 1 clashes with nothing in the reader: a header has no other effect than choosing the table, and a profile that has both `[routing]` and `["routing"]` behaves as one with `[routing]` twice (the first value of a key wins, which TOML itself would call a duplicate table). Option 2 would make a valid profile warn about a form it can read, and the warning text says "write it under [routing]", which is what the reader now does for them. The reader only catches more: every header that was `[routing]` or flagged misplaced still is, and no header that was another table became routing except the two quoted forms.
