# Decision 551-1

- **Date:** 2026-11-28
- **Decision:** `has-records --pr`'s hint for a missing `check` record names both real routes and no longer ends in "Then harvest." (#551). It reads: "run the local gate (coordinate step 6.1) on this sha again: mark-check.mjs --record writes it, or harvest if a `Checks:` or `Code review:` comment at this sha carries the check line." The job and review hints keep "Then harvest."; the `--issue` output is unchanged.
- **Options considered:** (1) Do what the issue says literally: drop "Then harvest." and leave the old hint, which names only `mark-check.mjs --record`. (2) Name both routes (picked). (3) Keep "Then harvest." on every hint, as before the issue.
- **Why:** The issue says there is nothing to harvest for a check record. That was true when it was written, but since #441 (and #545) `harvest` keeps a `check` line from a pull request comment that reports the run: a `Checks: pass|fail @ <sha>` comment, or the reviewer's `Code review: ... @ <sha>` comment with a `Checks:` line later and an `insights.mjs line check` record. So a `check` record can be missing because the merge step skipped a harvest, not because the gate never ran, and "harvest" can fix it. Dropping every mention of harvest (option 1) would hide that route; the old unconditional "Then harvest." (option 3) sends the reader to a step that does nothing when no comment carries the line. The hint therefore says "or harvest if a comment at this sha carries the check line". This deviates from the issue's literal text (which would leave only the `mark-check.mjs --record` route); the issue's goal, that the hint stop sending a reader to a step that can't help, is kept. A test pins the `--pr` hint for each missing kind and the unchanged `--issue` hint.
