# Decision 572-1

- **Date:** 2026-11-28
- **Decision:** `validate` refuses a job record's `started` or `ended` that reads as a time (`Date.parse` gives a number) and doesn't end in `Z` or a `+hh:mm` / `-hh:mm` offset, naming the field. Text that is no time at all (`yesterday`) stays valid, as does a time with an offset (`+01:00`). The usage-window report's edges (a reset exactly at `started`, a reset at `ended` when it differs from `at`, a bad `started` or `ended`) and both mixed orders of "Fixed it" are pinned by tests; no report wording or behaviour changed (#572, from the review of #563).
- **Options considered:** (1) Reuse the strict `at` check (`isoUtc`: exactly what `toISOString` writes, with milliseconds). It doesn't fit: 62 of the 65 `started` values on main are `date -u +%Y-%m-%dT%H:%M:%SZ` (no milliseconds), and the writer's callers keep passing that form. (2) Refuse every `started` or `ended` that isn't a `Z` time, `yesterday` included. `AC-129-2` passes `started=yesterday` and `started=...+01:00` to `insights.mjs line job` and expects exit 0 and a run line saying unknown; a refusal would make that existing test fail, and tests are never weakened. (3) The chosen rule: refuse only what reads as a time with no zone, the case where `Date.parse` uses the reader's local zone.
- **Why:** A zone-less time is the one value that makes the report's start and end, and so its crossed-reset rule, depend on the machine that reads it. Text that is no time already gives no duration and no start bound (the report falls back to `at` and to the end alone, now pinned), so it can't be misread. An offset names its zone and `Date.parse` honours it. Every record under `docs/insights/` on main passes, tested.
- **Originator:** AI pick, not reviewed (Full automation). The issue says to require a zone and to reuse the `at` check if it fits; the picks are the exact rule above (a `Z` or an offset; no-time text left valid) and the wording of the message.
