# Decision 378-1

- **Date:** 2026-11-27
- **Decision:** `coordinate` checks the size first, in step 6.1.1 right after `own-branch.mjs` exits 0, before the clone, the checks and any review. Exit 1 sends the pull request to a fresh builder on the same branch with the split brief. The first send-back isn't a review round, so it doesn't count toward the review cap. A later head of the same issue still at 1,000 or more counts as a failed review round, so the review cap and its escalation (`routing`'s two steps, then a split through `issues` on Full) take over and the send-backs end. A child of a size split (its issue says `Split from #<n>`) gets no free send-back of its own: its first head at 1,000 or more counts as a failed review round (#418). The `Sent back` line goes on the issue too, not only on the pull request, and the coordinator looks for it there before it calls a send-back free (#418). In local mode, `pr-size.mjs` gets a `--head <ref>` option, so the loop counts a branch from its checkout of main with main's own copy of the script, never the head's copy and never by switching its checkout. `references/local-mode.md` runs this check before its review from the diff. In pull request mode, `--head` is refused (exit 2): the script counts GitHub's head there.
- **Options considered:** rely on `pr-rules.mjs` in 6.1.3, after the install and `check` (a full gate run spent on a pull request that goes back anyway); a new step between 6.1 and 6.2 (renumbers steps other issues and tests cite); a bullet under 6.1.1, as above. For local mode: switch the checkout to the branch (then the branch's own copy of the script runs), run it in a worktree of the head (`pr-size.mjs` counts the checkout it sits in, so main's copy still counts main), or a `--head` option, as above.
- **Why:** #378 asks for the size check before review and a split brief instead of a review. Counting first costs one API read and spares the clone, install and checks. A size send-back is the cut being too big, not a finding about the code, so counting the first one toward the cap would push a split issue to the cap early. With no bound at all, though, a builder that keeps coming back over the limit gets fresh builders without end on Full (review round 1 of #412), so the second one counts. `pr-rules.mjs` keeps its size rule in 6.1.3, so a head that grew after the count still fails.
