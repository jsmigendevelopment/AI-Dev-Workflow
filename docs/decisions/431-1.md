# Decision 431-1

- **Date:** 2026-11-28
- **Decision:** The `job` record takes four optional fields next to the usage readings: `usage_window_before`, `usage_window_after` (the window a reading is for, as the tool names it: lower case, digits and underscores, up to 40 characters, such as `seven_day`) and `usage_resets_before`, `usage_resets_after` (when that window resets: a UTC time exactly as `toISOString` writes it). Each is `unknown` or left out when the tool doesn't show it, and each goes only with its own reading (`usage_before` or `usage_after`), which may itself be `unknown`, because a tool can show the window and reset with no percentage (the `rate_limit_info` of a cloud session does). The writer, `validate` and both readers are the existing ones: the format is the one master, `scripts/insights-record.mjs`. `build`, `pr-review`, `pr-security` and `qa` pass them where the tool shows them (`rateLimitType` and `resetsAt`), never estimated.
- **Options considered:** two fields, one window and one reset time per record (the issue's wording: it can't say whether the two readings name different windows, which the issue also asks for); four fields, one pair per reading, as above; a single `usage_window` object (the record format has no object field, and an object needs its own strict checks). A free-text window with no pattern (decision 380-2's way for the readings: it would let a newline or a made-up sentence into a field the report compares for equality). A fixed list of windows (a new window name from the tool would be refused, and the record lost).
- **Why:** The report compares the two readings' windows and checks a reset time against the run, so each reading needs its own pair. A pattern keeps the compared text to what a tool really names, without a list that goes stale. A reset time held to the same form as `at` can be compared as a time and can't fake a second line (decision 411-1).
